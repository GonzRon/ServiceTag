# ServiceTag local automation API, version 1

Introduced in ServiceTag **1.1.0** (issue #46) and **extended additively in 1.2.0** with the
maintenance surface — groups, schedules, completion, postponement, round closure and due work. The
version stays **1**: every 1.2 change is a new route, a new response field or a new error code, and
nothing a 1.1.0 client relied on moved. 1.3.0 added references the same way, and **1.4.0** adds
seasons, the maintenance break, service policy, operational condition, derived health and the
attention list — still at version **1**. 1.4 is additive too, with one change a 1.3 client can
notice: the schedule command's three season fields are now **deprecated inputs**, translated through
one table and refused by name where they cannot describe what 1.4 stores (see **Deprecated
inputs**). **1.4.1** adds two routes that repair schedules whose reminders no provider delivers, and
gives a create that omits `providers` the row the app's editor writes (see **Repairs**, and the
schedule command under **Bodies**) — still at
version **1**. This document is the contract. The wire and the
route table are `app/src/main/kotlin/com/loosecannon/servicetag/api/`, tested in
`app/src/test/kotlin/com/loosecannon/servicetag/api/`; the merge semantics of the last two
sections are `core/src/main/kotlin/com/loosecannon/servicetag/core/merge/` and
`core/…/usecase/{BuildBackupMergePlan,ApplyBackupMergePlan,ImportBackupMerge}.kt`, tested in
`core/src/test/kotlin/com/loosecannon/servicetag/core/{merge,usecase}/`.

## Where it is, and when

- **Address:** `127.0.0.1`, port **17337**. Nothing else is ever bound, and an accepted connection
  whose peer is not a loopback address is closed before a byte of it is read.
- **Lifetime:** the listener runs while **Settings > Utilities > Developer API** is the screen on top
  and the activity is resumed. Pausing (screen off, lock, app switch) stops it; leaving the screen
  stops it. There is no service, no background work, no boot hook and no way to start it without
  that screen in front of the owner.
- **Reaching it from a workstation:** `adb forward tcp:17337 tcp:17337`. The MCP server in
  `tools/servicetag-mcp/` does this itself.
- **The permission, and what it does not mean.** The app declares
  `android.permission.INTERNET`, because Android gates the *creation* of a TCP socket on the group
  that permission grants, whatever address the socket is bound to. On stock Android it is an
  install-time permission that cannot be denied; some hardened Android builds let the user revoke
  it. The app never requests it at runtime: the screen explains a denial and links to the app's
  settings page (**If it cannot start**, below). The README's
  [permission inventory](../../README.md#permissions) lists the permissions the app declares and the grants it uses.
  `INTERNET` gives the process network capability. The Developer API's listener binds only to localhost; the app's one intentional outbound use is **Save as document** (#85), an https download of a reference's document, made when the owner taps it on the phone, or when the owner's paired workstation asks through the Developer API while its screen is open (`POST /v1/references/{id}/materialize`, **Save as document (#92)**, below). A paired workstation that can create a reference can therefore have the phone download any public https document, under every restriction #85 sets on the download.
  `app/src/main/kotlin/com/loosecannon/servicetag/fetch/UrlConnectionTransport.kt` is the only
  `HttpURLConnection` in the app, and there is no `OkHttp` and no `WebView`; future cloud features may
  make intentional outbound use of the permission under their own designs.
- **If it cannot start:** when port 17337 is already taken the listener does not come up, and when
  a listener that did come up stops accepting connections on its own it is closed; either way the
  screen says so — `The Developer API could not start. Leave this screen and open it again.` —
  because leaving and returning is a fresh session, a fresh code and a fresh attempt. When the
  network permission is denied the screen says instead
  `ServiceTag is not allowed to use the network, so the Developer API cannot start. Allow network access in the app settings, then close ServiceTag and open it again.`
  with an `Open app settings` button beneath it that opens the app's own settings page.
  `Requests this session` staying at 0 corroborates a listener that never came up, and a logcat
  carries one `Log.w` line for it with no token, no path and no body.

## Authentication

Every request must carry:

```
Authorization: Bearer <pairing code>
```

The pairing code is the eight characters shown on the Developer API screen. It is drawn from
`SecureRandom` over the 32-character alphabet `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (no `I`, `O`, `0` or
`1`), is **case-sensitive**, and is **new every time the screen opens**. It is held in memory for
that visit only: never saved state, never a preference, never a log line.

Anything without a valid code — no header, the wrong prefix, the wrong code, the right code in the
wrong case — gets:

```
HTTP/1.1 401 Unauthorized
Content-Length: 0
```

and **nothing else**. The check happens before routing, so an unauthenticated caller cannot learn
which paths exist — the one thing a 413 still lets them tell apart, from the size at which it is
raised, is which body tier a request is in: one of the two 4 MiB import paths, since #92 a `POST` on
the 256 MiB attachment upload shape (`/v1/assets/{id}/attachments`, where a declared 64 KiB + 1 is
answered 401, not 413), or the ordinary 64 KiB tier. The comparison is
`java.security.MessageDigest.isEqual`.

**The upload is authenticated before its body is read (#92).** Every other body is read off the socket
before the code is checked; the attachment upload's is not. Its code is checked on the request line
and headers alone, so a 401 there never reads, stages, hashes or decodes a byte of the body: the
phone answers the empty 401 and closes the connection after the same bounded drain every answer
gets — at most 4 MiB, within 5 s of wall clock. A client that streams a large body without waiting
for an answer may therefore see the connection reset rather than the 401. Read a small route first
(the MCP reads `GET /v1/status`), and a stale code shows up there.

## Framing and limits

One request per connection; the answer always carries `Connection: close`.

Every refusal in this table answers with an **empty body**: a framing refusal happens before the
pairing code is checked, so the status is all it may say — in particular a 413 does not name the
path or its ceiling. Every refusal *past* authentication (a bad field, an unknown route, a domain
conflict) carries the full JSON error body described under **Errors**.

A trailing slash is dropped before anything else: `/v1/assets/` is `/v1/assets`, and
`/v1/import-merge/plan/` gets the import ceiling, not the small one.

| limit | value | over it |
|---|---|---|
| methods | `GET`, `POST`, `PATCH`, `DELETE` | 405 |
| request line | 8 KiB | 400 |
| header block | 8 KiB **of bytes**, 64 headers | 400 |
| body | **64 KiB** | 413 |
| body, the two `POST /v1/import-merge/*` paths only | **4 MiB** | 413 |
| body, `POST /v1/assets/{id}/attachments` only (#92) — any other method on that shape keeps 64 KiB | **256 MiB** (268,435,456 bytes), streamed, never held in memory | 413 |
| idle connection | 5 s | dropped |
| `Transfer-Encoding` | refused in any form | 400 |
| a `POST` or `PATCH` with no `Content-Length` header, even one with no body at all | refused | 400 |
| a body on `GET` or `DELETE` | refused | 400 |

Only one connection is answered at a time: there is one client and one call at a time, so nothing
interleaves. A second caller waits in a backlog of 4 or is refused.

**Long writes (#92).** An upload of up to 256 MiB, or a save as document of up to ten minutes plus
its copy into the folder, holds that one connection for its whole length: every other call — the
status, the reads, the writes — waits unaccepted in the backlog meanwhile, and a fifth connection may
be refused. A call that times out on the client while it waits is still in the backlog, and it runs
when it is reached; only its answer is lost, so a write that "timed out" can land minutes later.
Treat a timed-out write as an unknown outcome — read before you run it again — and keep one call in
flight. A `Content-Length` above 2,147,483,647 is the shipped 400 on every path; one above the
upload's 256 MiB is the pre-authentication 413, and because that body goes unread the connection may
be reset before the 413 arrives, as an over-cap import's may.

A query string is ignored — no endpoint reads one, so nothing may come to depend on one.

## Bodies

Requests are `Content-Type: application/json`, UTF-8, except `POST /v1/import-merge/plan` and
`POST /v1/import-merge/apply`, which are `Content-Type: application/zip`, and — since #92 — the
attachment upload, whose body is the document's own bytes in the document's own type
(**Attachments (#92)**, below; that path never answers 415). The wrong type is a
**415**. Note that `/v1/import-merge` with nothing after it is **not a route**: it is a 404, and it
gets the ordinary 64 KiB ceiling, not the bigger one.

**Unknown fields are rejected.** A misspelled field is a 400 naming it, rather than an edit silently
dropped.

**Response rows are the backup format's own shapes.** `AssetDto`, `NfcTagDto`,
`MeasurementDefinitionDto`, `EventProfileDto`, `AssetEventDto`, since 1.2 `MaintenanceGroupDto` and
`OccurrenceClosureDto`, since 1.3 `AssetReferenceDto`, since 1.4 `SeasonActivationDto`,
`AssetConditionDto` and `HealthSubjectDto`, since #79 `ServiceCaseDto` and `ServiceCaseEntryDto`, since
#86 `AssetSuccessionDto`, since #92 `AttachmentDto` (its source keys **sensitive**, **Attachments (#92)**),
and since #15 `SupplyItemDto` (its `SupplySpecificationDto` rows nested) and `AssetSupplyDto`
are the `@Serializable` classes
`data.json` inside a backup archive carries, produced by the same mappers
(`core/src/main/kotlin/com/loosecannon/servicetag/core/backup/BackupFormat.kt`). A row read here and
that row in an archive are the same JSON object, field for field. That is one schema on purpose:
there is nowhere for the API and the backup format to drift apart.

Every field is present in every response (defaults are encoded), so a client never has to
distinguish absent from default.

**The schedule row is the one exception to "a response row is the archive row"** (1.4). Format 8
took 1.3's three season fields out of `MaintenanceScheduleDto`, and `/v1` still reports them, so
every response that carries a schedule carries **the format-8 row plus a derived compatibility
triple**, as one flat object: every `MaintenanceScheduleDto` field in its order — `servicePolicy`,
`policyOffsetDays` and `ruleChangedAt` included — then `seasonBehavior` (**nullable** since 1.4),
`seasonReentry` and `seasonReentryOffsetDays`. The triple is derived from the row's own policy and
offset and stored nowhere:

| `servicePolicy` | `seasonBehavior` | `seasonReentry` | `seasonReentryOffsetDays` |
|---|---|---|---|
| `CONTINUOUS` | `IGNORE` | `null` | `null` |
| `IN_SERVICE_AT_START` | `FOLLOW_ASSET` | `AT_START` | the offset |
| `IN_SERVICE_RESUME_CLAMPED` | `FOLLOW_ASSET` | `RESUME_CLAMPED` | `null` |
| `PRE_SERVICE` | `null` | `null` | `null` |

`ruleChangedAt` — the instant the schedule's recurrence last changed, the never-terminated pin's
floor — is response-only: no command takes it.

**One response shape is *not* in the backup format, on purpose.** `ScheduleStateDto` — the derived
state `GET /v1/schedules/{id}` and `GET /v1/due` report — is a **read projection**: every field of
it is recomputable from configuration, events, closures, membership and today, `ScheduleRecompute`
is the only thing that ever writes the row, and **no archive carries it and no command accepts
one**. Derived state that travelled in an archive would be derived state that could arrive stale, so
the "one schema on purpose" rule above deliberately stops short of it. `schedule_local_delivery` —
the snooze and the notification bookkeeping — is device-local and appears on this API not at all,
and so, since #79, does `deadline_local_delivery`, the warranty warning's.
1.4 adds three more projections on the same footing — the **season**, **health** and **attention**
responses — each computed for the day it names and stored nowhere, and #79 a fourth, the
**warranty** response. **No health value exists in any
table, column or archive**; health is computed at read time, every time.

**`installationId`** (#92, additive) is this ServiceTag installation's id: 16 random bytes from a
`SecureRandom`, written as 8-4-4-4-12 lowercase hex, with no meaning inside it. It is **opaque,
random and device-local** — not a hardware, Android or adb identifier, not a model or a host name,
and **not authentication material**: the pairing code stays the only credential. It is made the first
time something asks for it, kept in a file the phone's backups do not carry, and then stable across
restarts and upgrades; it changes only when the app's data is cleared or the app is reinstalled. It
is **never in a backup, an export, a merge or a Transfer Pack**, so a phone seeded from another's
export still has its own. Its one use is the upload's id derivation (**Attachments (#92)**, below).
If its file cannot be read or written, `/v1/status` is the shipped 500 `internal`.

**Both `…/archive` routes answer with the row (200), not 204**, matching `POST /v1/assets/{id}/archive`.

**`POST …/complete` dispatches on the schedule's target, never on the body.** An asset-targeted
schedule records one completion of its own asset. A group-targeted one records one **member's**
completion, and the body's `assetId` says which member — so completing a five-member round is five
calls, and a round only advances once every required member is done. A member already recorded for
the round answers **409 `SCHEDULE_OCCURRENCE_TAKEN`**; a body with no `assetId` on a group target
answers **422 `COMPLETION_MEMBER_REQUIRED`**.

**The body of `close-round` is optional in its *field*, not in itself.** `closedOn` may be left
out, but the request still needs `Content-Type: application/json` and a body — `{}` is the minimum —
because the wrong or missing content type is a 415 raised before the serializer is reached. That is
the same rule the shipped `…/archive` routes already follow.

**"Close this round" is the one way to end a round nobody finished**, and it never claims anybody
did the work: it writes a single immutable `occurrence_closure` row, no column on the schedule and
no event on any asset. `closedOn` defaults to today and may be any date from the round's **open
date** through today, inclusive; anything outside that is **422 `CLOSED_ON_OUT_OF_RANGE`**. In 1.2
it is offered on **group-targeted** schedules only, and only on a round that obliges somebody. The
next round opens the moment a round is closed — its open instant is the closure's `createdAt`.

**1.2.1:** it is also refused before the current round reaches its own due-soon window — from
`effectiveDueOn - leadDays` through today it is allowed exactly as before, and calling it any
earlier is **409 `OCCURRENCE_NOT_YET_OPEN`**, writing nothing. `effectiveDueOn` is `postponedDueOn
?: computedDueOn` (the same value `GET /v1/schedules/{id}` reports), so a round postponed into the
future is not closeable until its own postponed window opens; clearing the postponement
(`POST …/postpone` with `postponedDueOn: null`) is the way to close it sooner. A closure always
advances the schedule, so a repeated `close-round` the same day, once the first has succeeded,
lands on the freshly opened next round rather than the one just closed — and this guard holds
against that retry **whenever `leadDays` is less than the recurrence interval**. With a lead at or
beyond the interval, the next round is already inside its own window when the first closes, so the
retry is **accepted** and writes a second closure: this is a known limit of 1.2.1, not a bound the
guard enforces. A client that lost a 201 should still read `GET …/closures` before retrying rather
than sending the call again — the only reliable way to tell "my first call succeeded" from "it was
never due" is comparing the `occurrenceOn` a 409 `OCCURRENCE_NOT_YET_OPEN` reports against the
closures already on record.

**Derived schedule state.** `GET /v1/schedules/{id}` answers `{schedule, state, status,
computedForOn}`. `state` is `ScheduleStateDto`:
`{scheduleId, lastCompletedOn, lastCompletionEventId, lastCompletedMeter, currentMeter,
computedDueMeter, lastTerminationEffectiveOn, lastTerminationKind, computedDueOn, effectiveDueOn,
actionableDueOn, policyReason, policyPhase, quiet, seasonActive, computedForOn, computedAt}`.
`status` is one of `OK`, `DUE_SOON`, `DUE`, `OVERDUE`, `INACTIVE_SEASON`, `PAUSED`, `NO_DATA` and,
since 1.4, `DEFERRED` — **never stored, computed at read time** — and `lastTerminationKind` is
`COMPLETED`, `CLOSED` or `NONE`.

**1.4's four state fields.** `actionableDueOn` is the day the work is actionable under the
schedule's service policy, and it sits **beside** `effectiveDueOn`, whose meaning is unchanged
(`postponedDueOn ?: computedDueOn`). `policyReason` says why the two differ: `NONE`,
`SEASON_START`, `AFTER_BREAK`, `BEFORE_SEASON`, `BEFORE_BREAK`, `POLICY_INAPPLICABLE` or
`AWAITING_START`. `policyPhase` is `ACTIVE` or `DORMANT` (held while its asset is out of season), and
`seasonActive` is 1.3's field, answered as `policyPhase == ACTIVE`. `quiet` is true while today is
inside the asset's maintenance break under a non-`CONTINUOUS` policy: late work stays late, and is
quiet. **`DEFERRED`** is the status of a time side the break is holding — inside its own lead,
before its actionable date, with the meter side (if any) not due: it never counts as due and never
notifies, and it is decided after the two sides are folded, so a crossed meter threshold is never
hidden behind it.

**The state is derived for today on every read** (1.4). Every route builds it from the stored row
when that row was rebuilt today, and otherwise derives it in memory — a row stored before a season
or break boundary is never believed and **never written back**; no read route writes anything.

**`computedForOn` appears twice.** The **top-level** one is the local date `status` was computed
for — today, always. `state.computedForOn` is the day that derivation is for, which since 1.4 is
also today: the stored row's own column when it was rebuilt today, and today when the state was
derived in memory. `state.computedAt` is when that derivation was made.

**`GET /v1/due`** answers the same projection the app's dashboard and Maintenance screen read, in
the same order, so a client can reproduce what a person sees without re-deriving it. Each item is

```
{scheduleId, targetKind ("ASSET"|"GROUP"), assetId, groupId, title, status, effectiveDueOn,
 actionableDueOn, policyReason, quiet, computedDueMeter, currentMeter, lastCompletedOn,
 lastTerminationEffectiveOn, lastTerminationKind, completionMode, membersRequired, membersComplete,
 rank}
```

Every field is present, with `null` where there is no value. `rank` is the item's 0-based index in
the attention order — dense and ascending. **Since 1.4 that order follows `actionableDueOn`**, not
`effectiveDueOn`, and a `DEFERRED` item sits in its own Deferred section after the current ones, so
`rank` does too; `actionableDueOn`, `policyReason` and `quiet` mean what they mean in the state
above, and `status` may be `DEFERRED`. A group-targeted schedule is **one** item carrying
`membersRequired`/`membersComplete` and is counted **once**, however many members are outstanding;
an asset-targeted one carries `null` for both. An **archived** schedule appears here in no
circumstance.

**An edit replaces every field its command carries.** `PATCH /v1/assets/{id}`,
`PATCH /v1/events/{id}`, `PATCH /v1/groups/{id}`, `PATCH /v1/schedules/{id}`,
`PATCH /v1/health-subjects/{id}` (1.4), `PATCH /v1/service-cases/{id}` (#79), `PATCH /v1/loans/{id}` (#72), and `POST /v1/definitions`
or `POST /v1/profiles` with an `id` are full replaces of the command's fields, not partial updates. The body is the complete new
state: an optional field left out is cleared, not kept, and a list left out becomes empty. Four
exceptions, each spelled out with its command below: a definition's blank `key` keeps the stored
key, a profile's blank `defaultTitle` becomes the profile's name, a health subject's omitted
`sortOrder` keeps the subject's place, and an asset's identity and lifecycle
(`id`, `status`, `retiredOn` and `createdAt`) are not in the command at all, and `templateKey` is
accepted but ignored on an edit — retiring and archiving stay on their own endpoints, and a PATCH
never changes either. On an asset that includes `parentAssetId` — leave it out and a component
becomes a top-level asset — and `warrantyExpiresOn`, which takes the warranty reminder lead with it
(#79): the lead is in no command, so a PATCH that keeps the date keeps `warrantyReminderLeadDays`, and
one that leaves the date out clears both. On a **group** it includes the member list: a member left out of
`PATCH /v1/groups/{id}` is **soft-removed**, which stamps `removedAt` on its membership row and
deletes nothing — every past round's required set is unchanged, and re-adding that asset later
inserts a new row with a new id. On a **schedule** it includes every optional rule field, but
**not** `postponedDueOn`, `status` or `archivedAt`, each of which has its own route. On a **service
case** it includes the repair link, `resolutionEventId` — leave it out, or send `null`, and the case no
longer names a repair record — but **not** `status` or `closedOn`, which move only through a status
entry (`POST /v1/service-cases/{id}/entries`), and not `assetId` or `incidentEventId`, which never move:
a case `PATCH` naming any of the four is the unknown-field 400 and writes nothing. On a **loan** it is the
open loan's terms — `lentOn`, `dueOn`, `reminderMode` and `notes`: leave out `dueOn` and the loan has no
due date, leave out `reminderMode` and it is `NONE`, and a mode other than `NONE` without a `dueOn` is
refused, never quietly reset — but **not** `returnedOn`, which only `POST /v1/loans/{id}/return` sets, and
never `assetId` or `borrowerName`, which the lend sets and nothing moves afterwards, or the contact link,
which no loan route takes: a loan `PATCH` naming any of those three is the unknown-field 400 and writes
nothing, and a returned loan refuses every `PATCH`.

**A request shape is a subset of a response shape.** A response row carries identity and
bookkeeping no command accepts — an asset's `id`, `status`, `createdAt`, `updatedAt` and
`retiredOn`; a reading's `sortOrder`, `archivedAt`, `createdAt` and `updatedAt`; a quick action's
`templateKey`, `sortOrder`, `archivedAt`, `createdAt` and `updatedAt`, and its field and consumable
rows' `sortOrder` (and a field's `id`) — and unknown fields are rejected, so a row read here
cannot be sent straight back. Since 1.2: a group's `id`, `archivedAt`, `createdAt` and `updatedAt`
and each membership row's `addedAt` and `removedAt` (a membership `id` **is** in the command, and
names a window to keep); a schedule's `id`, `status`, `createdAt`, `updatedAt` and
`postponedDueOn`. The schedule command is one rename apart from its row as well: the row reports
`assetId`/`groupId`, the command takes **`targetAssetId`/`targetGroupId`**, because the pair is a
choice of target and not two fields of a row. Since 1.4: a schedule's `ruleChangedAt`, and — because
its row reports both the policy and the derived 1.3 triple — a schedule row sent back whole is refused
as `LEGACY_AND_CURRENT_FIELDS_MIXED` before its identity keys are even read; send one form. A health
subject's `id`, `archivedAt`, `createdAt` and `updatedAt` (and, on its `PATCH`, its `assetId`); an
activation's or a condition's `id`, `assetId` and `createdAt`, the asset being the path's. Since #79: an
asset's `warrantyReminderLeadDays`, which only `POST /v1/assets/{id}/warranty-reminder` writes — a body
naming it on the asset command is the unknown-field 400. A service case's `id`, `status`, `closedOn`,
`createdAt` and `updatedAt` (and, on its `PATCH`, its `assetId` and `incidentEventId`), and a timeline
entry's `id`, `caseId` and `createdAt`, the case being the path's. Since #72: a loan's `id`,
`contactLinked`, `returnedOn`, `createdAt` and `updatedAt` (and, on its `PATCH`, its `assetId` and
`borrowerName`), the return date going only to `POST /v1/loans/{id}/return`. To change one field: read the record, copy across only the fields
the command below lists, change the one you mean, and send that. An event is further apart still —
`GET /v1/assets/{id}/events` reports parsed `measurements`, while `PATCH /v1/events/{id}` reads
`values` as `{definitionId: "as typed"}` — so a logged event cannot be reconstructed from its own
response; send every field of the event you intend it to have.

The MCP server in `tools/servicetag-mcp/` adds a convenience layer over this, and the two layers
are not the same thing. **This API's edits are full replacements. The MCP edit tools are
PATCH-like.** On an edit, `update_asset`, `save_definition`, `save_profile`, `update_group`,
`update_schedule`, `postpone_schedule`, (1.4) `update_health_subject`, (#79) `update_service_case` and
(#72) `update_loan` read the row's current fields, overlay only the arguments they were given, and submit
the complete replacement for you; `update_asset`, `update_schedule`, `update_health_subject`,
`update_service_case` and `update_loan` send **every key their command has**, from a copy of
`docs/api/command-shapes.json` vendored into the MCP package (the subject's without `assetId`, the case's
without `assetId` and `incidentEventId`, the loan's without `assetId` and `borrowerName`), so a key the
command gains is carried without a tool learning its name. `update_loan` reads the loan through
`GET /v1/loans/{id}` and never sends a return date, a borrower or a contact link.
`update_service_case` never sends a status or a `closedOn` — they are in no command — and carries the
stored `resolutionEventId` forward like any other field, so an edit never silently unlinks a repair
record. An **omitted**
argument and one sent explicitly as **`null`** both leave the current value
alone — the same thing, deliberately: a client that bridges to strict function calling sends `null`
for every optional argument its caller did not set, so if `null` meant "clear", a one-field rename
would silently wipe the rest of the row. Clearing is therefore explicit and **by name**, through
`clear_fields` (`save_profile` needs none: its fields are text or lists, where `""` and `[]`
already clear). `update_event`, `complete_schedule`, `close_round`, (1.4) `start_season`,
`end_season` and `record_condition`, and (#79) `add_case_entry` are the exceptions with no overlay
at all — every one of their arguments is required, because a logged event's response shape cannot be
converted back into its request shape, and a completion, a closure, an activation, a condition or a case's
timeline entry is a **new fact** with nothing about it to inherit from a row. The other 1.4 writes — `set_season_mode`,
`set_maintenance_break`, `set_health_policy`, `create_health_subject` and
`archive_health_subject` — are commands sent as given, and so are #79's `set_warranty_reminder` and
`open_service_case`, and #72's `lend_asset` and `return_loan`;
`update_asset` never sends the warranty reminder lead, because it is not a key of the asset command.
The MCP's `create_schedule` and
`update_schedule` keep 1.3's `season_behavior`, `season_reentry` and `season_reentry_offset_days`
as **deprecated arguments**: one of them sends this API's legacy form, exactly as given and
translated only here (see **Deprecated inputs**), and one mixed with `service_policy` or
`policy_offset_days` is refused by the MCP before any request, with this API's own
`LEGACY_AND_CURRENT_FIELDS_MIXED`. And every MCP write first reads `GET /v1/status` once per
pairing and refuses an app whose `schemaVersion` is below 8 with **`APP_SCHEMA_TOO_OLD`** — the
MCP's own code, never this API's — sending nothing; reads, and the merge plan, still work against
an older app. #79's two tools, `get_warranty` and `set_warranty_reminder`, read and write alike, refuse
an app below schema 11 the same way, because their routes are not there, and its five case tools —
`list_service_cases`, `get_service_case`, `open_service_case`, `update_service_case` and
`add_case_entry` — an app below schema 12, and #72's five loan tools — `list_loans`, `get_loan`,
`lend_asset`, `update_loan` and `return_loan` — an app below schema 13. None of that is this API's behaviour: on the wire, a field left out is cleared. Anyone
changing the MCP layer should read `tools/servicetag-mcp/README.md` §"Editing an existing row"
before making it agree with this page.

**The asset command** takes `name` (required) and, all optional: `category`, `description`, `notes`,
`manufacturer`, `model`, `serialNumber`, `purchaseOn`, `inServiceOn`, `purchasePriceMinor`,
`currency`, `vendor`, `location`, `warrantyExpiresOn`, `warrantyNotes`, `parentAssetId`,
`seasonStartMmdd`, `seasonEndMmdd`, `templateKey`. Dates are ISO `YYYY-MM-DD`; `purchasePriceMinor`
needs a `currency`. `seasonStartMmdd`/`seasonEndMmdd` are `MM-DD`, not a full date — for example
`04-01` — and both or neither must be given.

**`category` is stored in its catalog spelling** (#74). A create or an update promotes it: the
first save of a category keeps the spelling as typed, in Unicode NFC, with invisible characters such
as zero-width spaces, word joiners, soft hyphens, bidi marks and controls, and tag characters outside
the England, Scotland and Wales flags removed (the meaningful joiners and the variation selectors are
kept), the space-like blanks (the Hangul fillers, the braille blank) read as spaces, trimmed and runs
of spaces collapsed, and its key is that spelling lowercased. A later variant of it, or of a built-in,
is stored — and answered — in the spelling already saved, so a response may differ from the request
by case, spacing, normalisation or invisible characters (a `POST` of `water` after `Water` answers
`Water`, and `hot  TUB` answers `Hot tub`). There is no categories route.

**1.4 keeps the asset command exactly as 1.3 shipped it**, and condition is never part of it. Its
season pair is now a **compatibility input**: a pair makes the season `CALENDAR` and none makes it
`YEAR_ROUND`, and the pair an asset already reports is always accepted unchanged. A **different**
pair on a `MANUAL` asset is **422 `LEGACY_WRITE_CANNOT_REPRESENT`** and writes nothing, and a pair
change that would remove or re-kind the boundary a `PRE_SERVICE` schedule counts back from — taking a
`CALENDAR` season away, or adding a pair to a `YEAR_ROUND` asset whose break is that boundary — is
**409 `SEASON_MODE_STRANDS_POLICY`** (adding a boundary where there was none is allowed). The mode itself, the break and the health policy have their own
routes (below). The **asset row** reports five 1.4 fields beside the pair, as the archive row does:
`seasonMode` (`YEAR_ROUND`｜`CALENDAR`｜`MANUAL`; the pair is set exactly when it is `CALENDAR`),
`blackoutStartMmdd` and `blackoutEndMmdd` (the maintenance break, both or neither),
`healthAggregation` (`TRACK_ONE`｜`AVERAGE`｜`WEIGHTED`｜`WORST`) and `healthPrimarySubjectId` (set
exactly with `TRACK_ONE`). No command on this route sets any of the five. **Since #79 (format 11) the
row also reports `warrantyReminderLeadDays`**: whole days before `warrantyExpiresOn` that the phone
warns, or `null` for no reminder — never set while `warrantyExpiresOn` is not. No command on this route
sets it either: `POST /v1/assets/{id}/warranty-reminder` does (**Warranty reminders (#79)**, below).
The warranty's **status** is derived, and is on no row: it has its own response.

**Save-definition** takes `assetId` and `label`, plus optional `id`, `key` (blank generates on a
create and keeps on an edit), `unit`, `kind` (`ENTERED`｜`DERIVED`), `valueType`
(`NUMBER`｜`TEXT`｜`BOOLEAN`), `decimals` (0–4), `rangeLow`, `rangeHigh`, `isMeter`, `formula`
(`PERCENT_DROP`), `sourceAId`, `sourceBId`. Once measurements exist, `valueType`, `kind` and `key`
are frozen and a change to any of them is a 409.

**Save-profile** takes `assetId`, `name`, `eventKind`, plus optional `id`, `defaultTitle`, `fields`
(`[{definitionId, required}]`, each an ENTERED reading of the same asset) and `consumables`
(`[{id, name, defaultQuantity, unit, supplyId}]`; `supplyId` since #15, **Asset supplies (#15)**).

**Event** takes `assetId`, `kind`, `occurredOn`, `tzId`, plus optional `profileId`, `title`,
`occurredTime` (`HH:MM`), `notes`, `values` (`{definitionId: "as typed"}`) and `consumables`
(`[{name, quantity, unit, supplyId}]`; `supplyId` since #15). `kind` is one of `MAINTENANCE`, `INSPECTION`, `MEASUREMENT`,
`TREATMENT`, `INCIDENT`, `REPLACEMENT`, `SEASON_START`, `SEASON_END`, `NOTE`, `CUSTOM`.

**The group command** takes `name` (required) plus optional `description` and `members`
(`[{id?, assetId, sortOrder}]`). A member's `id` names an existing membership window to **keep**; a
line with no `id` is an **add**, and an add for an asset that already holds an open window is
**422 `MEMBER_ALREADY_OPEN`** — the caller meant "keep it", and the way to say that is to send its
`id`. `addedAt` and `removedAt` are server-stamped and are in no command, so no caller can open,
move or close a window by writing a date.

**The schedule command** takes `title` (required) plus, all optional: `targetAssetId`,
`targetGroupId`, `description`, `timeInterval`, `timeUnit` (`DAY`｜`WEEK`｜`MONTH`｜`YEAR`),
`timeBasis` (`FIXED`｜`COMPLETION`), `anchorOn`, `leadDays`, `meterDefinitionId`, `meterInterval`,
`anchorMeter`, `meterLead`, `servicePolicy`, `policyOffsetDays`, `completionMode` (`QUICK`｜`FORM`),
`profileId`, `remindersEnabled` and `providers` (`[{provider, enabled}]`) — and, as **deprecated
inputs**, 1.3's `seasonBehavior` (`IGNORE`｜`FOLLOW_ASSET`), `seasonReentry` and
`seasonReentryOffsetDays`, never in the same body as `servicePolicy`/`policyOffsetDays` (see
**Deprecated inputs**). **Exactly one of the two targets must be set**, and at least one of the two
rule sides — a time rule (`timeInterval` + `timeUnit` + `anchorOn`) or a meter rule
(`meterDefinitionId` + `meterInterval`). A **group** target is narrower still: no meter rule, no
`profileId`, `completionMode` `QUICK` only, **`CONTINUOUS` only** in either form, and the group must
already have a member. Dates are ISO `YYYY-MM-DD`. **Omitted `providers` on a create (1.4.1):** the
row gets one `LOCAL` provider with `enabled` equal to `remindersEnabled` — what the app's editor
writes; send `"providers": []` to store none. On a PATCH an omitted `providers` still means an empty
set (a full replace replaces everything) and a `null` is still refused.
`docs/api/command-shapes.json` lists every command's keys, the schedule's deprecated ones and its
action flag included, and a JVM test holds each request class to it.

**The service policy** (1.4) says when a schedule's work is actionable relative to its asset's
season and break; it moves only the time side's date, never the meter's:

| `servicePolicy` | means | `policyOffsetDays` |
|---|---|---|
| `CONTINUOUS` (the default) | whenever it is due | `null` |
| `IN_SERVICE_AT_START` | dormant while its asset is out of season; a date earlier than the season's start plus the offset moves to that day (a later one is never dragged back); a `YEAR_ROUND` asset is never out of season, so there it only waits out the break | `0`–`365` days after the start; **omitted or `null` is `0`** |
| `IN_SERVICE_RESUME_CLAMPED` | dormant while out of season; its own date, but not before the season starts | `null` |
| `PRE_SERVICE` | actionable before the season starts — or, with no calendar season but a break, before the break — by the margin, and never earlier than the occurrence opened | `-365`–`-1`, **required**: nothing suggests one |

Under either `IN_SERVICE_*` policy, and for `PRE_SERVICE` work whose point lies after it, a date
inside the asset's maintenance break moves to the first day after the break; work already late stays
late and is `quiet`. `CONTINUOUS` ignores the season and the break.

A meter-only schedule may take an `IN_SERVICE_*` policy for dormancy, with offset `0`; `PRE_SERVICE`
or a non-zero offset on one is **422 `SEASON_POLICY_NEEDS_A_TIME_RULE`**, and any other offset
outside its policy's range is **422 `POLICY_OFFSET_INVALID`** (`field` `policyOffsetDays`).
`PRE_SERVICE` on an asset with neither a calendar season nor a break is **409
`PRE_SERVICE_NEEDS_DATES`** — the remedy is the asset.

**The action flag `unlinkHealthSubject`** (1.4) is taken by `PATCH /v1/schedules/{id}` and
`POST /v1/schedules/{id}/archive`, and is an action, not a field: no row carries it, and a create
refuses it as an unknown field. While a live health subject is driven by a schedule, an edit that
removes the schedule's time rule or moves it to another asset or a group, and archiving it, are
**422 `SCHEDULE_DRIVES_HEALTH_SUBJECT`** naming the subject; the same request with
`"unlinkHealthSubject": true` succeeds and archives that subject in the same write — or, when the
subject is the one its asset's `TRACK_ONE` health follows, is **409 `HEALTH_SUBJECT_IS_PRIMARY`**
and writes nothing. Every other edit is unguarded, and the flag with nothing to unlink changes
nothing.

**Postpone and snooze, and health** (1.4, O-6). `POST /v1/schedules/{id}/postpone` moves this
occurrence's canonical due date, and under 1.4 that date passes through the service policy — so a
postponement **may restart maintenance-overdue health from the new actionable date**. That is
intended, not a defect: the owner re-agreed when the work is due. A **snooze** is device-local, has
no endpoint, delays only the reminder, and **never changes health**.

**The completion command** takes `occurredOn` and `tzId` plus optional `occurredTime` (`HH:MM`),
`notes`, `values` (`{definitionId: "as typed"}`), `consumables` (`[{name, quantity, unit, supplyId}]`) and
`assetId`. Since #15 a completion's lines may carry `supplyId`, on the same terms as an event's
(**Asset supplies (#15)**); a completion sent without lines writes no line, so it names no supply item. `assetId` is **required** for a group-targeted schedule, where it names the member who
did the work and is validated as a member this round obliges; for an asset-targeted one it must be
absent or that schedule's own asset. Any valid past `occurredOn` is accepted, and the date sent is
the date stored. `occurrenceOn` is **not** in the command: it is stamped from the schedule's own
computed due date at write time — never the postponed date — which is what keeps a round's key
immutable. A completion of a `FORM` schedule sent with no `values` and no `consumables` is accepted
and records `detailsPending: true`, so the one-tap path exists and still says the form is owed.

**The merge report** is
`{formatVersion, backupSetId, applicable, assets, groups, definitions, profiles, schedules,
closures, links, tags, events, attachments, references, seasonActivations, conditions,
healthSubjects, categories, serviceCases, caseEntries, loans, transfers, successions, supplyItems,
assetSupplies, installedComponents, conflicts, duplicateCandidates}`. Each of its
twenty-three tables is `{insert, identical, conflict, skipped}` — seven since 1.1.0, plus `groups`,
`schedules` and `closures` since format 6, plus `references` since format 7, plus `seasonActivations`,
`conditions` and `healthSubjects` since format 8, each in write-order position, plus `categories` since
format 9, listed after them although a merge writes categories first, plus `serviceCases` and
`caseEntries` since format 12, plus `loans` since format 13, plus `transfers` — the transfer records,
`OUT`, `IN` and `WITHDRAWN` — since format 14, which a merge writes last,
plus `successions` — the asset successions — since format 15, listed after the transfer records although a
merge writes them before, plus `supplyItems` and `assetSupplies` — the supply items, then their
applicability rows — since format 18, listed after them whatever order a merge writes them in, plus
`installedComponents` — the installed components, each with its composition — since format 19, listed last.
The `categories` tally counts the archive's
category rows **and** the rows the plan adds for the categories its inserted assets need. `applicable` is true exactly when `conflicts` is empty —
it is the only field a client has to read to know whether an apply will do anything. Each conflict
is `{table, id, verdict, reason, detail}`, sorted by table order then id, with `reason` one of the
stable codes below. Each duplicate candidate is `{incomingAssetId, localAssetId, hint}` and never
makes `applicable` false.

### The reference surface (1.3.0)

Three more rows. A **reference** is a URI on an asset — a manual on the web, a note in Joplin — with
no bytes of its own: it is a pointer to something that lives somewhere else, and the byte-bearing
rows are attachments, which this API neither read nor wrote before #92 (**Attachments (#92)** and
**Save as document (#92)**, below).

| method | path | body | success | notes |
|---|---|---|---|---|
| `GET` | `/v1/assets/{id}/references` | — | 200 | `{references: [AssetReferenceDto]}`, by `displayName`, each row carrying `role` since #91. The **ninth** `/v1/assets/{id}/…` sub-resource, so a verb it does not take is a **404** |
| `POST` | `/v1/references` | `{assetId, uri, displayName, description, role?}` | 201 | `{reference}`; `role` absent or `null` is no role. A verb this shape does not take is a **405** |
| `PATCH` | `/v1/references/{id}` | `{displayName?, description?, role?}` | 200 | `{reference}`; `null` leaves `displayName` or `description` alone, `""` blanks the description; **`role` is three-state** — absent leaves it alone, `null` clears it, a name sets it. An amend that changes nothing is a 200 carrying the stored row, and `updatedAt` does not move |

**No command carries `kind`.** It is **derived from the URI's scheme**, returned **read-only** in the
row, and an **unknown field on both commands** — so a body naming it is a **400** naming it, exactly
as any other misspelled field is. A client reads the derived value and can never set it, correct it
or disagree with it. `kind` is one of `WEB_URL`, `NOTE_LINK`, `OTHER`.

`uri` and `assetId` are unknown fields on the `PATCH` for the same reason: the URI is stored exactly
as it was validated and is never edited, and a reference cannot change owner — re-parenting is a
delete on the phone plus a fresh `POST`. So the `POST` body is five fields and the `PATCH` body is
three, and the response shape stays a **superset** of the request shape: `id`, `kind`, `scheme`,
`createdAt` and `updatedAt` are response-only.

**An unfamiliar scheme is a refusal here, never a confirmation.** In the app an unknown scheme is
saved once the person has been asked about it by name; there is nobody on the wire to ask, so over
this API it answers `REFERENCE_SCHEME_BLOCKED` exactly as a hard-blocked scheme does, and writes
nothing.

**A document role on a web link (#91).** Since schema 17 a reference whose `kind` is `WEB_URL` — an
`http` or `https` link — may carry the same document `role` an attachment does: `PURCHASE_INVOICE_OR_RECEIPT`,
`USER_MANUAL` or `SERVICE_MANUAL`. Every row carries the key, a name or `null`, in every list and in every
`POST` and `PATCH` answer. The role is **only ever the one a command gave**: no route infers one from the
URI, the scheme, the kind, the name or the description, so a reference named "User manual" sent with no
`role` has none. A role on a `NOTE_LINK` or `OTHER` reference is **422 `REFERENCE_ROLE_NOT_ALLOWED`**,
`field` `role`, and nothing is written; an unknown role name is the decoder's **400**. The role never
changes the `kind`, which is still the scheme's alone. On the `PATCH`, `role` is the one key whose `null`
is a value: `{"role": null}` clears it, a body without the key leaves it alone, and a body that sends
the stored role and nothing new is the unchanged 200. The `PATCH` body is decoded as typed first, so
every shipped 400 and 415 is unchanged, and then read once more only to see whether it names `role`; a
body the typed decoder would take that is not strict JSON — two keys with no comma between them — is
therefore the **400** here and on **Save as document (#92)**, below, where it was taken before #91. On
the phone a reference's role is drawn only on its own row — the asset's Key documents and its purchase
document read attachments only — and it reaches an attachment only through Save as document.

Fourteen more rows over eleven new path shapes, at version 1. Every write calls exactly one use case —

| `POST` | `/v1/health-subjects` | health-subject command | 201 | `{subject}` |
| `GET` | `/v1/health-subjects/{id}` | — | 200 | `{subject}` |
| `PATCH` | `/v1/health-subjects/{id}` | health-subject command **without** `assetId` | 200 | `{subject}`; **full replace** |
| `POST` | `/v1/health-subjects/{id}/archive` | `{"archived": true｜false}` | 200 | `{subject}`; archive is the only way a subject leaves |
| `GET` | `/v1/attention` | — | 200 | `{items: [...]}` (below) |

The seven new `/v1/assets/{id}/…` shapes are sub-resources, so a verb one does not take is a
**404**, and so is a wrong verb on `/v1/health-subjects/{id}/archive`; `/v1/health-subjects`,
`/v1/health-subjects/{id}` and `/v1/attention` answer **405**.

**The season mode** is `YEAR_ROUND` (always in season), `CALENDAR` (in season between
`seasonStartMmdd` and `seasonEndMmdd`, `MM-DD`, wrapping — both required, and only `CALENDAR` takes
them) or `MANUAL` (in season from a recorded `START` to the next `END`). `manualPhase`
(`IN_SEASON`｜`OUT_OF_SEASON`) is an action parameter taken **exactly** on a switch into `MANUAL`
from another mode — the switch records one `START` or `END`, dated today — and refused everywhere
else. A command equal to the stored mode and window writes nothing. A change that would remove or
re-kind the boundary a `PRE_SERVICE` schedule counts back from is **409
`SEASON_MODE_STRANDS_POLICY`**; adding a boundary where there was none never is.

**The maintenance break** is `{blackoutStartMmdd, blackoutEndMmdd}`: both or neither, `MM-DD`,
wrapping, never covering every day of a year (**422 `BLACKOUT_COVERS_THE_YEAR`**), and nothing ever
fills it in for you. A change that would strand a `PRE_SERVICE` schedule is **409
`BREAK_STRANDS_POLICY`**. Both strands refusals list those schedules in `problems`, as
`StrandedSchedule(id=…, title=…)`.

**An activation** — `POST /v1/assets/{id}/season` — is `{action: START｜END, occurredOn?, eventId?}`.
`occurredOn` defaults to today and may be neither later than today nor, on a `MANUAL` asset,
earlier than its latest `START` or `END` (**422 `SEASON_DATE_OUT_OF_RANGE`**); `eventId` must name
an event of this asset (**422 `FOREIGN_EVENT`**). Then the stored state: **409 `SEASON_NOT_MANUAL`**,
**409 `SEASON_ALREADY_STARTED`** or **409 `SEASON_ALREADY_ENDED`** — a `MANUAL` asset with no row
reads out of season, so its first `END` is refused. When a body refusal and a state refusal both
apply, the 422 is the one answered. An activation writes one immutable row and no asset field.

**The season response** is
`{seasonMode, seasonStartMmdd, seasonEndMmdd, seasonPhase, nextBoundaryOn, blackoutStartMmdd,
blackoutEndMmdd, inBreak, activations, computedForOn}`. `seasonPhase` (`IN_SEASON`｜`OUT_OF_SEASON`),
`nextBoundaryOn` and `inBreak` are what the mode, window and break mean on `computedForOn`.
`nextBoundaryOn` is the day a `CALENDAR` season ends while in season and its next start while out
of it, and `null` for `YEAR_ROUND` and `MANUAL`, whose next boundary is never predicted.
`activations` is the asset's whole `START`/`END` history, oldest first by `(occurredOn, createdAt,
id)` — kept, and unread, in every mode but `MANUAL`.

**Condition** is recorded, never inferred: `{condition: OPERATIONAL｜DEGRADED｜DOWN, occurredOn?,
occurredTime?, tzId, reason?, eventId?}`. `occurredOn` defaults to today and may not be later
(**422 `CONDITION_DATE_IN_FUTURE`**); `occurredTime` is `HH:MM` or absent; `reason` holds up to 500
characters, empty allowed (**422 `CONDITION_REASON_TOO_LONG`**); `eventId` must name an event of this
asset (**422 `FOREIGN_EVENT`**). Each call writes one immutable row and nothing else — no asset field,
no recompute. `conditions` is the whole history **oldest first by the ordering key**
`(occurredOn, occurredTime with none first, createdAt, id)` — not arrival order — and `current` is
its last row, or `null` when nothing has been recorded (which is not `OPERATIONAL`). A write's
`current` is read after it, so a backdated row is never claimed as current. Condition is in no
asset command.

**Recording a failure with its Incident.** The app's Change condition → "Log incident details" flow
records a DOWN or DEGRADED condition and the Incident that explains it together, in one transaction
(an Incident logged first and then answered "Mark down" or "Mark degraded" is two); the API keeps
them two calls, and adds no route or field for it. First `POST /v1/events` with
`{kind: INCIDENT, …}`, then `POST /v1/assets/{id}/conditions` with
`{condition: DOWN｜DEGRADED, …, eventId}`, `eventId` being the `id` of the event the first call
answered. They are two transactions, and the Incident is logged
once the first succeeds: never log it again. A refused second call (422) writes nothing — correct it
and send it again with the same `eventId`. A client that lost the second call's answer should read
`GET /v1/assets/{id}/conditions` before resending: a row whose `eventId` names the Incident means
the condition landed, and since a condition can never be amended or deleted, a blind resend would
leave a second row. Neither call writes the other fact — logging an `INCIDENT` records no condition,
and recording a condition logs no event.

**The health policy** — `{healthAggregation: TRACK_ONE｜AVERAGE｜WEIGHTED｜WORST,
healthPrimarySubjectId?}` — says how an asset combines its subjects. `TRACK_ONE` needs a primary
that is a live subject of the asset, and no other aggregation takes one (**422
`HEALTH_PRIMARY_INVALID`**). It writes the asset row alone.

**The health-subject command** takes `assetId` (on a create only), `name` (1–60 characters after
trimming), `kind` (`ASSET`｜`PART`｜`MEDIUM`), `driver` (`AGE`｜`MAINTENANCE_OVERDUE`) and the three
thresholds `nominalUntilDays`, `warningFromDays` and `criticalFromDays` — **required, with no
default**, `0 ≤ nominal < warning < critical ≤ 36500` — plus optional `scheduleId`,
`baselineProfileId`, `weight` (1–10, default 1) and `sortOrder` (omitted, it appends on a create and
keeps the subject's place on an edit). An `AGE` subject names no schedule and may name a
`REPLACEMENT` quick action of its own asset as its baseline; a `MAINTENANCE_OVERDUE` subject names
no baseline and one live, time-ruled schedule aimed at its own asset, which no other live subject
drives. A subject never changes asset, so `assetId` is an unknown field on the `PATCH`. Archiving the
subject its asset's `TRACK_ONE` health follows is **409 `HEALTH_SUBJECT_IS_PRIMARY`**; restoring one
re-checks its whole link. It is configuration only: no route writes a health value.

**The health response** is `{assetId, computedForOn, condition, aggregation, aggregate, subjects,
critical, components}`, computed at read time and stored nowhere:

- `condition` is `{condition, since, reason, occurredOn, eventId}` — the current row, `since` being
  the day its run of that word began — or `null`;
- `aggregation` is the asset's, and `aggregate` is `{score, band, trackedDays, fallback}`, or `null`
  when nothing contributes (**NOT TRACKED — never a 100**). `band` is `NOMINAL`｜`WARNING`｜`CRITICAL`;
  `trackedDays` is always `null` on the aggregate, which has no day count of its own; `fallback` is
  true when `TRACK_ONE`'s primary is gone and `WORST` was taken;
- `subjects` — the live ones, by `(sortOrder, id)` — are each `{subjectId, name, kind, driver,
  scheduleId, score, band, trackedDays, notTracked}`: a `score` (0–100) in a `band` with the
  `trackedDays` behind it, or `notTracked` with its reason, one of `NO_REPLACEMENT`,
  `PROFILE_REMOVED`, `OUT_OF_SEASON`, `SCHEDULE_PAUSED`, `LINK_INVALID`, `SCHEDULE_ARCHIVED` or
  `UNSCORABLE`. `UNSCORABLE` marks a subject whose own configuration is malformed; no command or
  restore can store one, so it is unreachable in practice and listed here for completeness;
- `critical` is `[{subjectId, name, score}]` for **every** subject scoring `CRITICAL`, whatever the
  aggregate says;
- `components` is `[{assetId, name, condition, reason, occurredOn}]` for every `DOWN` or `DEGRADED`
  in-service component **at any depth**, `DOWN` first, then by name.

So neither an average nor a band can hide a critical subject or a broken component, and a `DOWN`
asset's health is never shown without its condition.

**`GET /v1/attention`** lists the asset-level rows no schedule stands behind: every in-service asset
or component that is `DOWN` or `DEGRADED`, and every `AGE` subject scoring `CRITICAL` or `WARNING`.
A `MAINTENANCE_OVERDUE` subject never has a row here — it rides its schedule's row in `/v1/due`.
Each item is

```
{kind (CONDITION|HEALTH), section (ATTENTION|UPCOMING), assetId, parentAssetId, condition,
 reason, occurredOn, healthSubjectId, subjectName, band, score, rank}
```

with every field present, `null` when absent. A `CONDITION` row carries `condition`, `reason` and
`occurredOn` (its current row's) and null health fields; a `HEALTH` row the reverse; `parentAssetId`
names a component's parent. The conditions and `CRITICAL` are `ATTENTION`, `WARNING` is `UPCOMING`,
and `rank` is dense from 0 in the order `DOWN`, `DEGRADED`, `CRITICAL`, `WARNING`, then asset name
and id.

### Deprecated inputs (1.4.0)

The schedule command has **two forms**, and **key presence decides which**, read before anything
else about the body:

- a `servicePolicy` or `policyOffsetDays` key — **an explicit `null` counts as present** — is the
  **1.4 form**: an omitted `servicePolicy` is `CONTINUOUS` (a policy is never `null`, so
  `"servicePolicy": null` is the shipped 400), and an omitted or `null` `policyOffsetDays` is `0` on
  `IN_SERVICE_AT_START` and `null` otherwise;
- neither is the **legacy form**: 1.3's command, with 1.3's omitted-field defaults
  (`seasonBehavior` omitted is `IGNORE`);
- any of `seasonBehavior`, `seasonReentry` or `seasonReentryOffsetDays` **and** either 1.4 key in
  one body is **422 `LEGACY_AND_CURRENT_FIELDS_MIXED`**, and nothing is written; `problems` lists
  the keys found, the legacy ones first.

**The legacy form translates through one table** — the one the 7 → 8 migration and the format ≤7
decoder use, whose cases are committed as `docs/api/legacy-season-mapping.json`:

| `seasonBehavior` | `seasonReentry` | → `servicePolicy` | → `policyOffsetDays` |
|---|---|---|---|
| `IGNORE`, or omitted | anything | `CONTINUOUS` | `null` |
| `FOLLOW_ASSET` | omitted, `null`, `AT_START`, or anything else (an `MM-DD`, say) | `IN_SERVICE_AT_START` | `seasonReentryOffsetDays` when it is 0–365 **and** there is a time rule, else `0` |
| `FOLLOW_ASSET` | `RESUME_CLAMPED` | `IN_SERVICE_RESUME_CLAMPED` | `null` |

It normalises and never refuses a value; an unknown `seasonBehavior` name is still the shipped 400.

**Refused, never reset.** A legacy write that would change something 1.3's fields cannot describe
is **422 `LEGACY_WRITE_CANNOT_REPRESENT`** and writes nothing, in exactly two cases: a schedule
`PATCH` of a **`PRE_SERVICE`** schedule — whose row reads `null` in all three derived fields, so
sending them back is refused by name — and a **different season pair on a `MANUAL` asset** (the asset
command's one compatibility input). The remedy is the 1.4 form, or the season-mode route. Every other
legacy body translates, and a create clobbers nothing.

**One behaviour change.** A legacy body that says `FOLLOW_ASSET` and **omits `seasonReentry`** on an
`IN_SERVICE_RESUME_CLAMPED` schedule now makes it `IN_SERVICE_AT_START` at `0`: in 1.3 the field was
stored and never read. Send the `seasonReentry` the row reports to keep it.

**Reading stays compatible.** Every schedule response carries the triple, derived (see **Bodies**),
so `seasonBehavior` may now be `null`, and for every schedule 1.3 can describe, the triple sent back
in the legacy form lands on the same policy and offset. A 1.3 client keeps working on every schedule
it can describe and gets a named 422 on the rest — never a silent reset.

### Repairs (1.4.1)

Two more rows, for issue #80: before 1.4.1 a schedule created here with `providers` omitted stored
reminders **on** and **no provider row**, so nothing ever delivered its reminders. Both routes call
the one repair the app's Reminder Health screen calls, so there is one repair policy, not two.

| method | path | body | success | notes |
|---|---|---|---|---|
| `POST` | `/v1/repairs/schedule-providers/plan` | `{}` | 200 | the repair report. **Writes nothing.** |
| `POST` | `/v1/repairs/schedule-providers/apply` | `{}` | 200 | the same report, for the plan it made inside its own write, and what it repaired |

The body is `{}` as `application/json`: any key, or a zero-byte body, is the malformed-body 400;
another type is a 415 and another verb a 405.

**Which schedules.** A schedule is *matched* when it is not archived, `remindersEnabled` is true and
none of its providers is enabled. A matched schedule is *repairable* when it is `ACTIVE` and has no
provider row at all; every other matched schedule is *skipped*, with a reason — `PAUSED` for any
status but `ACTIVE` (status is judged first), `PROVIDERS_DISABLED` for a provider row that is there
and disabled, because a bulk repair never enables a provider someone turned off. An archived
schedule, or one with reminders off, is never matched. **Since #77, neither is a schedule whose target
is no longer maintained on this phone** — one on an asset that is archived, retired or transferred out
(**Transferred-out assets (#77)**, below), or on a group that is archived or wholly transferred out: the
same bound Reminder Health's own finding uses, so a bulk repair skips a transferred-out asset's schedule
and never meets its 409.

**What it does.** The apply gives each repairable schedule exactly one `LOCAL` provider,
`enabled: true`, and moves its `updatedAt`; nothing else on the row changes — not the rule, the
policy, `ruleChangedAt`, `postponedDueOn`, `profileId` or any history — and a skipped, archived or
reminders-off row is not written at all. **The plan writes nothing; the apply re-plans and writes; a
second apply repairs nothing.** Neither route runs a reminder sweep, like every other `/v1` write: the
repaired schedules are delivered from the next digest, backstop run or Reminder Health action.

**The report**, the same shape from both routes:

```
{matched, repairable, skipped, repaired,
 schedules: [{id, title, outcome (REPAIR|REPAIRED|SKIPPED), reason (PAUSED|PROVIDERS_DISABLED|null)}]}
```

`schedules` lists every matched schedule by title, then id. A plan says `REPAIR` for each schedule an
apply would repair and reports `repaired` 0; an apply says `REPAIRED` and reports `repaired` equal to
`repairable`.

### Warranty reminders (#79)

Two more rows over two new path shapes, at version 1. The warranty **status** is derived — from the
asset's stored `warrantyExpiresOn` and today — so it has a response of its own and is on no row, as the
season and the health are. The reminder **lead** is canonical: it is the asset row's
`warrantyReminderLeadDays`, it travels in a data archive from format 11, and one route writes it —
never the asset command.

| method | path | body | success | notes |
|---|---|---|---|---|
| `GET` | `/v1/assets/{id}/warranty` | — | 200 | `{warranty: {status, expiresOn, leadDays}}`, computed for today and stored nowhere |
| `POST` | `/v1/assets/{id}/warranty-reminder` | `{leadDays}` | 200 | `{asset, warranty}`; `leadDays` is required, and `null` turns the reminder off |

Both are `/v1/assets/{id}/…` sub-resources, the seventeenth and the eighteenth, so a verb one does not
take is a **404**, and an asset that is not there is the shipped **404 `no_such_asset`**.

**The warranty.** `status` is `IN_WARRANTY` while today is on or before `expiresOn` — the expiry day
itself is still in — `OUT_OF_WARRANTY` after it, and `NOT_RECORDED` when the asset has no warranty date,
or one that is not a date. `expiresOn` is the stored `warrantyExpiresOn` and `leadDays` the stored
`warrantyReminderLeadDays`, each `null` when there is none; every field is present. The answer is not
gated on the asset being in service: a retired or archived asset still reports its status and lead,
although the phone warns only for an in-service one.

**The lead** is whole days before the expiry date — 1 or more, with no upper bound — or `null` for no
reminder. The key has no default, so `{}` is a **400**, never a reminder silently turned off, and a lead
that is not a whole number (`1.5`, say) is the shipped **400** of a value that does not fit its type. A lead
under 1, or any lead on an asset without a `warrantyExpiresOn`, is **422 `warranty_reminder_validation`**
with `field` `leadDays`, and writes nothing (**The warranty reminder family (#79)**, below). The stored
lead sent again writes nothing; a change writes the asset row alone and moves its `updatedAt`.
**The date rule:** `warrantyReminderLeadDays` is never set while `warrantyExpiresOn` is not. The asset
command does not carry the lead, so a full-replace `PATCH /v1/assets/{id}` that keeps the date keeps
the lead, and one that leaves the date out clears the lead with it, silently — sending the date back
later does not bring the lead back. The app's editor refuses a lead without a date instead of clearing
it; both paths keep the rule.

**When the warning comes.** The warning is the phone's own, on the `warranty_reminders` channel: it
is posted once for each date and lead, by the first reminder sweep that finds an in-service asset inside
its window — from `leadDays` days before the expiry through the expiry day — whatever its season (a
restart inside the window may post it once more), and it is taken down when the date or the lead is
cleared, the asset is retired or archived, or the warranty has expired. It is
device-local: its bookkeeping, `deadline_local_delivery`, is never exported, merged or counted, and
there is no route or tool for the warning itself. **Neither route runs a reminder sweep**, like every
other `/v1` write: a lead set or cleared here — or cleared by a `PATCH` that clears the date — takes
effect at the phone's next digest (09:00 by default) or its 12-hour backstop. In the app, a save that
changes the date or the lead sweeps at once when notifications are already allowed; a lead first set
while they are not is announced at the next digest or backstop after the owner allows them.

### Service cases (#79)

Five more rows over four new path shapes, at version 1. A service case is an asset's record of an
outside repair or warranty claim: a **header** — the provider, a contact, the case or RMA number, its
type, coverage and status, both legs' tracking, the cost — and an append-only **timeline** of entries.
Both are canonical: they travel in a data archive from format 12 as `serviceCases` and
`serviceCaseEntries`, and each answers here as its archive row, `ServiceCaseDto` and
`ServiceCaseEntryDto`.

| method | path | body | success | notes |
|---|---|---|---|---|
| `GET` | `/v1/assets/{id}/service-cases` | — | 200 | `{serviceCases: [ServiceCaseDto]}`, the newest `openedOn` first, then by id; headers only |
| `POST` | `/v1/service-cases` | case command, plus `assetId` and optional `incidentEventId` | 201 | `{serviceCase}`; `OPEN`, with `closedOn` `null` |
| `GET` | `/v1/service-cases/{id}` | — | 200 | `{serviceCase, entries: [ServiceCaseEntryDto]}`, the timeline in its order |
| `PATCH` | `/v1/service-cases/{id}` | case command | 200 | `{serviceCase}`; **full replace** of the header's command fields — never its status or `closedOn` |
| `POST` | `/v1/service-cases/{id}/entries` | entry | 201 | `{serviceCase, entry}`; a status entry moves the header's status and `closedOn` |

The first is a `/v1/assets/{id}/…` sub-resource, the nineteenth, so a verb it does not take is a
**404**; the other three shapes answer **405** for a verb they do not take. An asset that is not there
is the shipped **404 `no_such_asset`**, and a case that is not there **404 `no_such_service_case`**.

**The case command** takes `title`, `type`, `openedOn` and `coverage`, all required and with no
default, and, all optional: `provider`, `contact`, `caseRef`, `outboundTracking`, `outboundCarrier`,
`returnTracking`, `returnCarrier`, `costMinor`, `currency`, `notes` and `resolutionEventId`. The open
also takes `assetId` (required) and `incidentEventId`. `type` is
`WARRANTY_SERVICE`｜`REPAIR`｜`OTHER_SERVICE` and `coverage` `IN_WARRANTY`｜`OUT_OF_WARRANTY`｜`UNKNOWN`｜`PARTLY_COVERED`
— the names the row carries; any other name is a **400**. `openedOn` is ISO `YYYY-MM-DD` and not after
today. Text is trimmed, blank text is `""`, and a blank `currency` is `null`. `costMinor` is minor units
of `currency`: `0` is no charge and is kept, `null` is no cost recorded, a negative cost is refused, and
a cost needs a currency of its own — an ISO 4217 code this build knows. `incidentEventId`, when given, names an `INCIDENT` of
this asset that no schedule completion logged; the API accepts a case with no Incident, although the
app opens every case from one. `resolutionEventId`, when given, names a `MAINTENANCE` or `REPLACEMENT`
event of the case's asset, a completion included; a stored link that no longer resolves passes when it
is sent back unchanged. Both links are soft: deleting the event leaves its id on the case.

**The API applies none of the app's form defaults.** The app's case editor suggests a coverage from the
warranty date, a type from that coverage, today's date and the asset's currency. This API stores exactly
what it is sent, so a body carries its own `type`, `coverage`, `openedOn` and `currency`: a cost with no
`currency` is refused even when the asset has one.

**The status moves only through a status entry.** A case opens `OPEN` with no `closedOn`, and no header
body carries `status` or `closedOn`: a `PATCH` naming either is the unknown-field **400** and writes
nothing. The `PATCH` is otherwise a full replace — an optional field left out is cleared,
`resolutionEventId` included, so leaving the repair link out or sending `null` removes it — and never
moves `assetId`, `incidentEventId`, `status`, `closedOn` or `createdAt`; the stored header sent again
writes nothing.

**An entry** takes `occurredOn` and `tzId` (required), `occurredTime` (`HH:MM`, or `null`), `note` (a string —
`""` or the key left out for none; `null` is refused **400** `bad_request`, as the 1.5.0 release gate observed) and
`status` (one of `OPEN`, `SENT_OUT`, `AT_SERVICE_CENTER`, `RETURNED`, `CLOSED` and `CANCELLED`, or
`null`): a note, a status, or both. `occurredOn` is not after today, and `tzId` is a zone this phone
resolves. A timeline is read in the order `(occurredOn, occurredTime with none first, createdAt, id)`.
An entry is immutable. A note-only entry writes the entry alone — the header, its `updatedAt`
included, is untouched. A status entry also sets the header's `status` and `updatedAt` in the same
write: `CLOSED` or `CANCELLED` sets `closedOn` to the entry's date, and any other status, reopening
included, clears it. Any status may follow any other, and entries apply in the order they are written,
whatever their dates.

**Nothing else moves.** No case route writes an event, a condition, a schedule or its state: closing a
case does not make the asset `OPERATIONAL` — the resolving event's own condition question does that, in
the app. Documents stay on the asset and on the linked events; a case owns none. A case on a retired or
archived asset is accepted.

### Loans (#72)

Five more rows over four new path shapes, at version 1. A loan records that an asset is out with a person
or an organisation: who has it, since when, when it is due back, and whether the phone should remind
the owner. It is canonical — it travels in a data archive from format 13 as `assetLoans` — and answers
here as a `LoanDto`: the archive row's fields, **less the Android Contacts link**, with `contactLinked`
in its place.

| method | path | body | success | notes |
|---|---|---|---|---|
| `GET` | `/v1/assets/{id}/loans` | — | 200 | `{loans: [LoanDto]}`, open and returned, the latest `lentOn` first, then by id |
| `POST` | `/v1/loans` | loan command, plus `assetId` and `borrowerName` | 201 | `{loan}`; open, with `returnedOn` `null`, and name-only |
| `GET` | `/v1/loans/{id}` | — | 200 | `{loan}`, open or returned |
| `PATCH` | `/v1/loans/{id}` | loan command | 200 | `{loan}`; **full replace** of an open loan's terms — never its borrower, its link or `returnedOn` |
| `POST` | `/v1/loans/{id}/return` | `{"returnedOn": "YYYY-MM-DD"}` | 200 | `{loan}`; "Mark returned", the only exit — the row stays as history |

The first is a `/v1/assets/{id}/…` sub-resource, the twentieth, so a verb it does not take is a **404**;
the other three shapes answer **405** for a verb they do not take. An asset that is not there is the
shipped **404 `no_such_asset`**, and a loan that is not there **404 `no_such_loan`**.

**`LoanDto`** is `{id, assetId, borrowerName, contactLinked, lentOn, dueOn, reminderMode, returnedOn,
notes, createdAt, updatedAt}`. `borrowerName` is the name the loan shows, trimmed and never blank.
`contactLinked` is `true` when the phone linked the loan to an Android contact; **the link itself — the
contact's lookup URI — is on no response and in no request**, and a body naming it is the unknown-field
**400**. Only the phone makes a link: its "Lend out" picks the borrower from Contacts, and "Choose from
Contacts" on an open loan relinks it, replacing the name and the link together. So every loan lent here
is name-only (`contactLinked` `false`) until the owner links it on the phone, and no route or edit here
moves a link the phone made. A data archive still carries the link, as data, through
`/v1/import-merge/plan` and `/v1/import-merge/apply`. Whether a loan is lent out or overdue is derived at
read time by the phone's screens and is not a field.

**The loan command** takes `lentOn` (required, no default) and, optional: `dueOn`, `reminderMode` and
`notes`. The lend also takes `assetId` and `borrowerName`, both required. Dates are ISO `YYYY-MM-DD` days,
never times: `lentOn` is not after today, and `dueOn`, when given, is not before `lentOn`; a blank or
`null` `dueOn` is no due date. `reminderMode` is `NONE`｜`ONCE`｜`UNTIL_RETURNED` — `NONE` when left out;
any other name, its case included, is a **400** — and a mode other than `NONE` needs a `dueOn`: without
one it is **refused**, never quietly reset to `NONE`. Text is trimmed. **The API applies none of the
app's form defaults**: the lend form offers today as the lent date, this API does not.

**One open loan per asset.** A lend to an asset that already holds an open loan is **409
`asset_already_lent`**, whatever else the body says, and writes nothing; `problems` names the open loan
(`AssetAlreadyLent(openLoanId=…)`), which is the one to return first. A returned loan does not block the
next. Any lifecycle may be lent here: the phone offers "Lend out" only on an in-service asset, but a
retired or archived asset is accepted, and its open loan stays visible and returnable on the phone.

**A returned loan is frozen.** "Mark returned" sets `returnedOn` — not before `lentOn`, not after today
— and the row stays, as the asset's lending history. After that, a `PATCH` or a second return is **409
`loan_returned`**, whatever the body says, and writes nothing. On an open loan the `PATCH` corrects the
terms, like the app's "Edit loan"; the stored terms sent again write nothing. The checks run in one
order, so a body that is both refused and wrong answers the first: a malformed body is the shipped
**400**, then a missing asset or loan the **404**, then `asset_already_lent` or `loan_returned` the
**409**, then every problem at once as **422 `loan_validation`** (**The loan family (#72)**, below).

**The reminder is the phone's.** A loan with a `dueOn` and a `reminderMode` of `ONCE` or `UNTIL_RETURNED`
is reminded on the phone's `loan_reminders` channel from the owner's digest hour on its due day — `ONCE`
once, `UNTIL_RETURNED` once a day until the loan is returned. It is device-local: its bookkeeping,
`deadline_local_delivery`, is never exported, merged or counted, and there is no route or tool for the
reminder itself. **No loan route runs a reminder sweep**, like every other `/v1` write: a loan lent or
re-dated here posts only at the phone's next reminder sweep **at or after the owner's digest hour** — the
digest, or the 12-hour backstop once that hour has passed — while a loan returned here has its standing
reminder taken down at the next sweep of any kind, the midnight sweep included. In the app, a save that
creates a loan or moves its due date or mode, and a return, sweep at once.

**Nothing else moves.** No loan route writes an event, a condition, a schedule or its state, or a health
value, and an overdue loan is never maintenance: it is not `OVERDUE`, not in `/v1/due`, and **not an
attention row** — `/v1/attention` is unchanged; the phone's Dashboard shows an overdue loan of an
in-service asset in a row of its own.

### Transferred-out assets (#77)

No new row. The phone can move selected assets to another ServiceTag installation in a **Transfer Pack** —
one `.zip` file around an ordinary data archive and its documents — and then mark them **transferred out**.
Making, sharing or saving a pack, importing one, marking and withdrawing are all **the phone's alone**: no
route or MCP tool creates, imports, marks or withdraws, and `AssetDto` has no transfer field. What reaches
this API is what those actions leave behind: the transfer records, the one refusal that protects a
transferred asset, and the merge rules that carry the records (**Table 19**, under **The additive merge
import**, below). The phone keeps a shared pack only while its ready screen is open — leaving the screen
deletes it — so an app that reads a shared pack lazily can find it gone; "Save a copy" keeps a lasting one.

**The records.** A transfer leaves append-only records, never updated or deleted — only a Replace restore
replaces the whole table with the archive's —: `OUT` (the asset left
this phone in a pack), `IN` (it arrived here in a pack — imported, or brought back) and `WITHDRAWN` (the
owner withdrew an `OUT`, on this phone). A withdrawal is **pack-wide and atomic**: it withdraws every
still-open `OUT` of that Transfer Pack in one write — "this pack did not leave" — and is refused, writing
nothing, if the estate it would leave behind still has a row pointing into a transferred asset. There is no
partial withdrawal: if only some of a pack's assets really left, withdraw the pack and transfer those again. They travel in a data archive from format 14 as
`transferRecords`, and `/v1/status` counts them under the same name. An asset is **transferred out** —
*held* — while this phone has an `OUT` for it that nothing closes. An `IN` closes an `OUT` of the same
asset when the `IN`'s pack lineage names the `OUT`'s pack (the asset came back) or the `IN` is of the
`OUT`'s own pack (the recipient's arrival, met in a merge); a `WITHDRAWN` closes the `OUT` it names. A
record names its asset by id alone, so the records outlive the phone's "Delete asset", which a held asset
still allows as the explicit way to forget its local history. Every later ordinary backup carries the
records in place of the transferred graph: it holds none of a held asset's rows.

**Held, whatever the status says.** Marking archives the asset on the phone, so an asset transferred out
from this phone normally reads `ARCHIVED`. But a held asset **may read `ACTIVE`**: an `OUT` that reached
this phone by an ordinary merge from another installation holds the asset here too, and a merge never
updates the asset's row. So `status` is not the test, and no field is: a client learns that an asset is
held when a write to it answers the 409 below. Every read route still answers for a held asset — it stays
inspectable — but it is no longer maintained here (below).

**Every mutation answers 409.** Every write route that reaches a row of a held asset answers **409
`asset_transferred_out`**, `problems` naming the held asset (**The transfer refusal (#77)**, below), and
writes nothing: the asset's own `PATCH`, `retire`, `archive`, `season`, `season-mode`,
`maintenance-break`, `health-policy`, `conditions` and `warranty-reminder`; a new asset or component under
it; its definitions, profiles, events, references, health subjects, service cases and their entries, and
loans; and a group that names it, or a schedule on it or on such a group — a group with any membership
row, current or removed, that names it included. **It is every mutation, not every change**: a full-body `PATCH` whose only difference
is the `category`, and an `archive` or `retire` that repeats the stored state, answer the 409 as well. Two
phone actions still reach a held asset, and no route performs either: "Delete asset", above, and the
category rename, which rewrites every asset of a category. **Validation comes first**: a body that fails its own checks
answers its own 400 or 422, on a held asset too, because the refusal fires at the write.

**Nor may a write gain a reference into a held graph.** A write to a row that stays — of an asset that is
not held — is refused the same way, 409 naming the held asset, when it would give that row a new hard
reference to a row a held asset owns: an event naming a held asset's schedule, profile or measured
reading, a health subject naming its schedule, a schedule naming its meter reading or its profile, a
profile naming its reading. A reference the row already carries — merged history can leave one — is not
a gain, so an edit that keeps it passes. But such a row blocks the phone twice: its next ordinary backup
refuses to export while a row still points into a transferred asset, and marking refuses while the
estate it would leave behind has one, because every backup after marking must leave the held graph out
cleanly. The way out: drop the reference — delete the pointing row, or edit it so it no longer names the
held row (a health subject is never deleted, so edit it; an event keeps its schedule on every edit, so
delete it), here or on the phone — or, on the phone, withdraw the Transfer Pack that holds the referenced
asset (refused, like any withdrawal, if it would leave the estate pointing into a transferred asset).

**Not maintained here.** A held asset is not maintained on this phone: none of its schedules is in
`/v1/due`, it has no row in `/v1/attention`, and it has no maintenance, warranty or loan reminder — the
reminder sweep withdraws each subject and takes down a standing post. #77 also corrects the rule for an
ordinary lifecycle: a live schedule on an **archived or retired** asset is now withdrawn from the reminders
too, where earlier builds kept reminding for it. A group's schedule stays in service while any member
stays. **No `/v1` write runs a reminder sweep**, so an archive or retire sent here, or a transfer record
merged here, settles at the phone's next sweep; the phone's own lifecycle and withdrawal actions sweep at
once. The provider repair skips such schedules too (**Repairs (1.4.1)**, above).

**Only a pack brings an asset back, and only on the phone.** A pack returns an asset here when its
lineage names this phone's `OUT` of the asset — one still open, or one withdrawn here, so a mistaken
withdrawal never strands a legitimate return — **and**, once its `IN` is recorded, no other `OUT` of the
asset stays open. If the lineage names this phone's `OUT` but another `OUT` of the asset stays open once
the `IN` is recorded — or the asset is held here and the pack does not name its `OUT` at all, a stale or
foreign pack — the import refuses, names that asset, and writes nothing; the way out of the first is to
withdraw, on the phone, the other Transfer Pack that asset is still recorded under, then import again. A pack asset that is neither held here nor
returning is imported additively, like any arrival. A return records its `IN` first, then replaces the
asset's stale graph here with the pack's, in one write; the returned loans this phone kept stay, as
history. **A pack is a bearer instrument by design**: whoever holds a pack whose lineage validly names
this phone's `OUT` brings the asset back, replacing its graph here — even when a withdrawal has since made
that asset live here again. The phone says so when it makes a pack.

**A Replace restore** — the phone's alone; no route restores — refuses, before it wipes anything, an
archive that carries the graph of an asset held here, unless the archive's own records hold a later `IN`
whose lineage closes that `OUT`. A backup from before the transfer never brings a transferred asset
back, while a backup the other installation made after a legitimate return still restores — the
operative rule being an archive `IN` whose lineage names this phone's `OUT`, so a first-hop recipient's
backup, whose `IN` lineage is `[]`, does not qualify.

**Merging between the two ends of a transfer.** After this phone (S) transfers an asset X to another (R)
and R imports the pack, ordinary merges between them run **one way while X stays with R: into R, from S**. S's
export merges into R — its `OUT` lands beside R's `IN` of the same pack, which closes it, so X stays live
on R. R's export into S is refused loudly: its `IN` would close S's open `OUT`, which is a `CONFLICT`
`ASSET_TRANSFERRED_OUT`, and so is a row it adds for X. A merge never moves custody; only a pack does,
and a withdrawal never travels in a merge either — an incoming `IN` or `WITHDRAWN` that would close an
`OUT` open here is that same conflict, so each installation withdraws its own.

**A double mark.** If two installations that share an asset — mirrors kept in step by merges — each mark
it out, in different packs, a merge between them meets **`TRANSFER_DIVERGED`** on the incoming `OUT`, its
`detail` naming both packs with the short ids their file names show. Resolve it on the phone that should
not have marked: withdraw its Transfer Pack there (every asset of that pack), then merge again, **in this order** — the export of the
installation that kept its `OUT` into the one that withdrew, then back. The other order meets
`CONTENT_DIFFERS` on the asset's row, because the withdrawing phone no longer holds the asset and exports
the row it archived at its own `updatedAt`.

**Withdrawing on both mirrors.** When an `OUT` that reached a mirror by merge is then withdrawn on both
installations, the asset is live on both, but its row still differs — archived, with a new `updatedAt`, on
the phone that marked it, and as it was on the other — so every later merge between the two meets
`CONTENT_DIFFERS` on that row. That is the shipped no-update limit: a merge never updates a row. The way
out is on the phone: a Replace restore of one mirror from a backup the other made after its own
withdrawal — neither phone holds the asset any more, so **A Replace restore**'s transfer check (above)
does not refuse it, though it still refuses one carrying an asset the restoring phone holds — after which
both hold the same row and the same records; like every Replace restore, it loses whatever the restored
phone had that the backup lacks, which cannot be merged across first while the conflict stands.

**A pack is not a data archive.** The import routes refuse the pack file itself (a 400 `archive_corrupt`,
or the 413 of a body over their limit). The `data.zip` inside a pack is an ordinary format-14 data
archive, and they will merge it within their 4 MiB limit — but only as an ordinary merge: it carries no
transfer records, so no `IN` is recorded; its documents are `SKIPPED` unless their bytes are already in
the phone's attachment folder; and nothing is replaced, so it never brings an asset back. An asset merged
that way has no lineage here, so a pack made of it later cannot return it to the phone it came from.
Import a pack on the phone.

### Asset successions (#86)

One more row over one new path shape, at version 1. The phone's **Replace asset**, on an asset's detail
screen, gives way from one asset to a *different* one: in one write it retires the old asset — unless it is
already retired — creates the new one as a new asset with a new id, carries forward only what the owner
ticked, as new rows, moves only the NFC tags the owner chose, and records the pair as one **succession**.
The old asset keeps its id and its whole history. A succession is canonical — it travels in a data archive
from format 15 as `assetSuccessions`, and `/v1/status` counts the rows under the same name — and answers here
as the archive's own row.

| method | path | body | success | notes |
|---|---|---|---|---|
| `GET` | `/v1/assets/{id}/succession` | — | 200 | `{replaces, replacedBy}`, each a succession row or `null` — **read only** |

It is a `/v1/assets/{id}/…` sub-resource, the twenty-first, so a verb it does not take is a **404**. An
asset that is not there is the shipped **404 `no_such_asset`**.

**The row** is `{id, predecessorAssetId, successorAssetId, replacedOn, createdAt}`, exactly the archive's
`assetSuccessions` row. `replaces` is the row that names the asset as its successor — the asset it
replaced — and `replacedBy` the row that names it as its predecessor — the asset that replaced it. Both keys
are always there. `replacedOn` is an ISO `YYYY-MM-DD` day, fixed when the succession is recorded: the old
asset's `retiredOn` at that moment — the date the owner gave when the replacement retired it, or the date it
already had — and it does not follow a later un-retire or re-retire.

**One in, one out, and no loops.** An asset is replaced at most once and replaces at most one. A chain is
rows — A replaced by B, then B by C, is two rows — so its middle asset answers both keys. Following
successors never comes back round.

**Recorded by a replacement.** No route amends or removes a succession, and `AssetDto` has no succession
field. A new succession is recorded only by a replacement: the phone's Replace asset or, since #92,
`POST /v1/assets/{id}/replace` (**Replacing an asset (#92)**, below), which is the same use case and the
same one write. It reaches another installation only as an archive's row: a Replace restore on the phone, or a
merge (`POST /v1/import-merge/apply`), which inserts it under **Table 20** and never updates it. This route,
the replacement's own three routes, the count and the merge report's `successions` tally are the whole of
it here. The
old asset's retirement is an ordinary `retiredOn`, and an un-retire of it
(`POST /v1/assets/{id}/retire` with `null`) leaves the succession as it is: the row is history.

**Deleting either asset deletes its succession.** Deleting an asset — the phone's alone; no route deletes
one — is destructive: it removes every succession that names it, at either end, and nothing is re-linked
around it, so deleting B from A → B → C leaves neither row, never an A → C. There is no unlink either: once
recorded, a succession stays until one of its two assets is deleted or a Replace restore replaces the table,
and nothing reverses a replacement.
That is a recorded limit of this first version.

**Transfers.** A succession is this phone's own lineage: it **never travels in a Transfer Pack** — a pack
that carries one is refused as damaged. While an asset at either end is transferred out from this phone,
every ordinary backup **leaves that succession out**, as it leaves the held asset's own rows out, and the
phone records no new succession naming a held asset. When a Transfer Pack brings an asset back, **this
phone's own successions naming it are re-inserted** unchanged, even when the asset at the other end is
still transferred out. A Replace restore — the phone's alone — replaces the whole table with the archive's;
an archive older than format 15 leaves none.

**Merging.** A succession merges on its own terms (**Table 20**, under **The additive merge import**,
below). **A merge never retires anything**, so the replacement lives on the phone that made it: merge
cannot carry it to a phone that holds the old asset unretired (below).

### Attachments (#92)

Four rows over two path shapes, at version 1. An **attachment** is a file on an asset or on a journal entry,
kept in the phone's attachment folder. These routes list an asset's attachments, read and amend one, and add
one to an asset **with its bytes**. **Nothing here deletes an attachment** — the API adds and amends, the
phone removes — and **no route returns an attachment's bytes**.

| method | path | body | success | notes |
|---|---|---|---|---|
| `GET` | `/v1/assets/{id}/attachments` | — | 200 | `{attachments: [AttachmentDto], folder}` — the asset's own, never its entries', oldest first (`createdAt`, then `id`) |
| `POST` | `/v1/assets/{id}/attachments` | the file's bytes, and the `X-ServiceTag-Attachment` header | 201, or **200** on a replay | `{attachment}` |
| `GET` | `/v1/attachments/{id}` | — | 200 | `{attachment}`, an asset's or an entry's |
| `PATCH` | `/v1/attachments/{id}` | attachment command | 200 | `{attachment}`; **full replace** of the five fields the command carries |

The first shape is a `/v1/assets/{id}/…` sub-resource, the twenty-second, so a verb it does not take is a
**404**; `/v1/attachments/{id}` answers **405** for a verb it does not take, `DELETE` included.
`/v1/attachments` and anything under `/v1/attachments/{id}/` are not routes: a 404. An asset that is not
there is the shipped **404 `no_such_asset`**, and an attachment that is not there **404
`NO_SUCH_ATTACHMENT`**. The list and the row read a transferred-out asset's attachments like any other.

**The row** is the archive's attachment row, field for field: `{id, assetId, eventId, kind, mode,
displayName, mimeType, sizeBytes, sha256, storageProvider, storageLocator, capturedOn, notes, createdAt,
updatedAt, role, sourceUri, sourceResolvedUri, sourceRetrievedAt, sourceName}`. **`sourceUri`,
`sourceResolvedUri`, `sourceRetrievedAt` and `sourceName` are sensitive** (R92-4): they are the provenance
Save as document records, `sourceUri` is the reference's URI verbatim and may carry a token from its own
query, and every export already carries them — so handle an answer that holds them as you would an export:
never log it, never paste it into an issue. The phone's own screens never show a full URI; that rule is
unchanged. `folder` is the attachment folder's state by name alone — `READY`, `NOT_CONFIGURED` or
`ACCESS_LOST` — never the folder's name or its provider.

**The attachment command** (the `PATCH`) is a full command: read the row, change what you mean to, send
every key back. A no-op answers 200 with the stored row, writes nothing, and `updatedAt` does not move.
The file, its locator, its size and digest and its provenance never move here.

| key | type | absent |
|---|---|---|
| `displayName` | string, trimmed; blank is refused | 400 |
| `kind` | `PHOTO`｜`LABEL_PHOTO`｜`RECEIPT`｜`MANUAL`｜`WARRANTY`｜`DOCUMENT`｜`OTHER` | 400 |
| `capturedOn` | `YYYY-MM-DD` or `null`; trimmed, and blank is `null` | `null` |
| `notes` | string | `""` |
| `role` | `PURCHASE_INVOICE_OR_RECEIPT`｜`USER_MANUAL`｜`SERVICE_MANUAL` or `null` — `null` clears it | 400: no default |

The checks run in one order: a malformed body is the shipped **400**, then the **404**, then a `capturedOn`
that is not a day **422 `ATTACHMENT_BAD_DATE`**, then a role on an entry's attachment **422
`ATTACHMENT_ROLE_NOT_ALLOWED`** (a document role belongs on an asset's attachment), then a blank name
**422 `ATTACHMENT_NAME_REQUIRED`**, and a row of a transferred-out asset **409 `asset_transferred_out`**.

**Adding a file.** `POST /v1/assets/{id}/attachments` takes the document's bytes as the body — raw: not
multipart, not base64, not JSON — and its description in one header:

- **`Content-Type`**: the document's own media type, lower-cased and stripped of parameters; absent, it is
  `application/octet-stream`. This path never answers 415.
- **`Content-Length`**: required, the exact byte count, at most 268,435,456 (256 MiB); 0 is refused below.
  `Transfer-Encoding` is refused, as everywhere.
- **`X-ServiceTag-Attachment`**: the unpadded base64url (RFC 4648 §5, no `=`) of this UTF-8 JSON object.
  Absent, padded, not base64url, not UTF-8, not JSON, an unknown key or an unknown name is the **400
  `bad_request`**. It shares the 8 KiB header block, so a long note is better set by `PATCH` afterwards.

| key | | |
|---|---|---|
| `operationKey` | required | 1–128 characters of `A–Z a–z 0–9 . _ ~ : -`, the request's idempotency key (below) |
| `displayName` | required | trimmed; blank is refused |
| `sha256` | required | 64 **lowercase** hex characters, the body's SHA-256 |
| `kind` | optional | an `AttachmentKind` name; absent or `null`, the server infers it from the normalised type: `image/*` is `PHOTO`, `application/pdf` is `DOCUMENT`, anything else `OTHER` |
| `role` | optional | a `DocumentRole` name; absent or `null` is **no role**. A role is **never inferred** — not from the name, the type or the kind (R92-5) |
| `capturedOn` | optional | `YYYY-MM-DD`; trimmed, and blank is none |
| `notes` | optional | defaults to `""` |

There is no provenance key: an upload never records where a file came from; only Save as document does.
The keys are pinned in `command-shapes.json` as `attachmentUpload`.

**An answer on this path is written only after the whole declared body has been read** — into staging on
the way to the folder, into a hashing sink on a replay, or into a counting sink when a refusal was decided
first — so a refusal is an answer, never a reset. Before a body byte is read the phone checks, in order:
the header (**400**); the asset (**404 `no_such_asset`**); that it is not transferred out (**409
`asset_transferred_out`**); the folder — none picked is **409 `ATTACHMENT_STORE_NOT_CONFIGURED`**, one whose
access was lost or that cannot be opened **409 `store_unavailable`**; then `operationKey` (**422
`OPERATION_KEY_INVALID`**), a blank `displayName` (**422 `ATTACHMENT_NAME_REQUIRED`**), `capturedOn` (**422
`ATTACHMENT_BAD_DATE`**) and `sha256`'s form (**422 `ATTACHMENT_SHA256_INVALID`**). Then, under the
long-write lock (below), the row id derived from the key is looked up: a row with that id makes this
a **replay**; otherwise the body is streamed into the app's cache staging in 64 KiB chunks, counted and
hashed — 0 bytes is **422 `ATTACHMENT_EMPTY`**, a digest other than `sha256` **422
`ATTACHMENT_SHA256_MISMATCH`** — and the phone's own add writes the file into the folder and the row in
one step: **201 `{attachment}`**. A staging write that fails (a full disk) is **409
`UPLOAD_NOT_STAGED`**; a folder that fails during the copy **409 `store_unavailable`**;
**422 `ATTACHMENT_TOO_LARGE`** is defence only, since the 413 comes first. If the installation id cannot
be read, the answer is the shipped **500 `internal`**, after the body was drained. Staging and the folder
both need room for the file at once.

**The body's own stream.** If the request's stream fails — the 5 s read timeout, a reset, the screen
leaving, or the **10-minute deadline over the whole body** — nothing is written, staging is discarded,
and **no answer is sent**: the connection closes. A body that ends before its `Content-Length` is the
**400 `bad_request`** "the body was shorter than Content-Length". Once the body is staged and the write
into the folder has begun, neither a disconnect nor the screen leaving can stop it: the outcome is one
attachment with its file, or none. After a lost answer, send the same request with the same key again.

**The operation key (R92-6, R92-7, R92-8).** The new row's id is derived from this installation, the
asset and the key:

```
uuid8(SHA-256(UTF-8("servicetag:attachment-upload:v2\n" + installationId + "\n" + assetId + "\n" + operationKey)))
```

— the digest's first 16 bytes with the RFC 9562 version-8 and variant bits set (byte 6 becomes
`(b & 0x0f) | 0x80`, byte 8 `(b & 0x3f) | 0x80`), in the lowercase 8-4-4-4-12 form. `installationId` is
`/v1/status`'s. `docs/api/attachment-operation-ids.json` holds golden vectors (installation id, asset id,
key → id) and golden cases of the kind the server infers. One installation derives the same id for the
same asset and key every time; two installations derive different ones, so the development and
production phones never give one id two contents. The id is an ordinary attachment id: it travels in
backups, merges and packs, while the installation id never does.

- **A replay answers 200.** When a row with the derived id exists, the body is read to its end and hashed
  but never staged; a digest other than `sha256` is **422 `ATTACHMENT_SHA256_MISMATCH`**. The request is
  then compared with **the row as it stands now**: the owner (this asset), `kind` (as given, else as
  inferred), `role`, the trimmed `displayName`, `sha256` and the size. All equal: **200 `{attachment}`**,
  the row, nothing written. `capturedOn`, `notes` and the media type are not compared, and a replay
  that differs only in them answers 200 without applying them.
- **Strict (R92-7).** Any compared value different is **409 `OPERATION_KEY_REUSED`**, `field`
  `operationKey`, `problems` `OperationKeyReused(attachmentId=…)` naming the row, and nothing is written.
  In particular, once the row has been edited, a replay that carries its original metadata under the
  same key is a 409. A metadata change belongs to `PATCH`, never to a replay.
- **A new key with identical bytes is a new row**, 201: the upload never refuses a file because the asset
  already holds the same bytes (Save as document does).
- A replay is answered only after the checks above: once the folder is unpicked, or the asset is
  transferred out or deleted, it answers that refusal, not 200. It checks the row's recorded digest, not
  the file in the folder.
- **Lifetime:** a key lasts exactly as long as its row, on this installation. Nothing expires; a row
  removed on the phone frees its key, and a replay then adds the file again. A restore onto another
  installation starts a fresh key space there.

**The long-write lock.** Uploads and saves as document take one process-wide lock, `apiLongWrites`, for
their writes; nothing else takes it. A retry of an upload whose answer was lost — even one on a new
listener after the screen was paused and resumed — waits for the first to finish and then finds its row,
200. The wait has no bound: a write stuck in the folder's provider holds every later upload and save as
document until the app's process restarts.

### Save as document (#92)

One more row over one new path shape. **Save as document** (#85) turns a web reference into an
attachment: the phone downloads the reference's https document, proves its type from its bytes, and keeps
where it came from. Since #92 the owner's paired workstation can ask for it too, for an **existing
reference, by id** — never for a URL sent on the wire (R92-3).

| method | path | body | success | notes |
|---|---|---|---|---|
| `POST` | `/v1/references/{id}/materialize` | `{displayName?, kind?, role?, notes?}` | 201 | `{attachment}`, its four `source…` keys filled — **sensitive**, as above |

A verb this shape does not take is a **405**; there is no other shape under `/v1/references/{id}/`.

**The body** is JSON, `{}` at least — an empty body is the **400**, another type the **415** — in the
ordinary 64 KiB tier, and every key is optional. For `displayName`, `kind` and `notes`, absent or `null`
takes the phone's own starting review: the reference's display name, the kind inferred from the proven
type, and the reference's description as the notes. **`role` is three-state** (#91): absent takes the
reference's own role (none when it has none, as no reference had one before schema 17), `null` is no
role, and a name is that role. The role is copied exactly, never guessed from the name or the type, and it
never chooses the `kind`. `kind` is an `AttachmentKind` name and `role` a `DocumentRole` name. The body
is decoded as typed first and then read once more only to see whether it names `role`, so a body that is
not strict JSON is the **400** (**The reference surface (1.3.0)**, above). **No key
carries a URL, a host or a path**: `url`, `uri` or any other key is the unknown-field **400**. The
document fetched is the one the stored reference names, read on the phone.

**A paired workstation that can create a reference can therefore have the phone download any public
https document**: `POST /v1/references` stores any https link (**The reference surface (1.3.0)**), and this
route fetches it. "Never a supplied URL" holds per route, not per session. The download keeps every one of
#85's restrictions: https on every hop, a host spelled only in plain ASCII (R85-15's authority rule — a
rule about how a host is written, not a list of allowed hosts) and the refusal of local addresses on every hop,
at most five redirects, 256 MiB and **ten minutes** at most, the nineteen proven document types, the fixed
`User-Agent: ServiceTag`, no cookie and no credential. The file lands in the attachment folder and never
comes back out — no route returns an attachment's bytes — and each host on the way sees a request from this
phone's network address, at that moment. No refusal body carries a URI, a host, a remote header or a
remote byte.

**It is synchronous.** One request downloads and commits; there is no job and nothing to poll. The answer
can take the download's ten minutes plus the copy into the folder (the MCP waits 720 s), and while it runs
**the API is busy**: every other call waits in the backlog (**Framing and limits**, above). A save waits
for the long-write lock behind an upload or another save, and that wait is not bounded.

The checks run in one order: a malformed body is the **400** or **415**; a given `displayName` blank after
trimming **422 `ATTACHMENT_NAME_REQUIRED`**; a reference that is not there **404 `NO_SUCH_REFERENCE`**; its
asset transferred out **409 `asset_transferred_out`** — all before any fetch. Then the lock, then the
download and its refusals:

- **409 `REFERENCE_NOT_MATERIALIZABLE`** — the reference is not an https document link by the phone's own
  rules; **409 `ATTACHMENT_STORE_NOT_CONFIGURED`** or **`store_unavailable`** — the folder; **409
  `NETWORK_DENIED`** — the app may not use the network.
- **502 `FETCH_…`** — the download was refused, by the remote, by the local-address rule once the host
  resolved, or by a rule a redirect broke; `problems`
  names the problem, such as `TimedOut` or `ServerError(code=503)`. `FETCH_UNREACHABLE`,
  `FETCH_INTERRUPTED`, `FETCH_TIMED_OUT` and a 5xx `FETCH_SERVER_ERROR` are transient; the rest are the
  remote's standing answer. **The MCP never retries a save as document on its own.**
- **409 `ATTACHMENT_ALREADY_HELD`** — the asset already holds an attachment with the same SHA-256 and
  size (R85-6); `problems` is `AlreadyHave(attachmentId=…)`, naming that row, and nothing is written. The
  check is made **after the whole download**, on the bytes that arrived — it is not a check of the link. It
  means "these bytes are already here", not "current": there is no force. A changed document at the same
  link has other bytes, so this route saves it as a new row (the MCP's tool does not re-save a link it
  already saved; the owner refreshes one on the phone).
- **404 `no_such_asset`** — the asset was deleted during the commit.

The reference itself is never written.

**When the screen leaves.** The download runs only while the Developer API screen is open. If the screen
leaves (a pause, screen off, another app) during the download, the download stops, nothing is written,
and **no answer is sent**: the connection closes. If it leaves after the commit began, the commit
completes — one attachment with its file — and still no answer is sent. A closed connection with no
answer is therefore **an unknown outcome**: re-read `GET /v1/assets/{id}/attachments` (a row whose
`sourceUri` is the reference's link is the saved one). Sending the request again downloads the document
again and answers **409 `ATTACHMENT_ALREADY_HELD`** only when the same bytes arrive; if the document at
the link changed, it is saved as a second row. A client that disconnects or times out does **not** stop
the download: the phone finishes it and may save the file after the client has given up.

**Recorded limits.** The phone's own Save as document sheet does not take the long-write lock, so a save
on the phone that overlaps one from here can leave two rows with the same bytes. The refusal codes are
the download's facts, so under DNS rebinding they tell the caller a little about an address — never a
byte of it. The MCP's 720 s is sized for the download and the commit: time the request spends in the
backlog or waiting for the lock counts against it, so a save queued behind another long write can time
out on the workstation while the phone still completes it — an unknown outcome (above).

### Replacing an asset (#92)

Three rows on the asset shape — the twenty-third, twenty-fourth and twenty-fifth `/v1/assets/{id}/…`
sub-resources, so a verb one does not take is a **404** — over #86's own Replace use case, the one the
phone's **Replace asset** calls: offer, plan, and one atomic write (R92-1). Nothing here is ticked for you
and nothing is defaulted.

| method | path | body | success | notes |
|---|---|---|---|---|
| `GET` | `/v1/assets/{id}/replace-offer` | — | 200 | what the old asset offers to carry forward. **Writes nothing** |
| `POST` | `/v1/assets/{id}/replace-plan` | the draft | 200 | the plan, even when blocked or with problems. **Writes nothing** |
| `POST` | `/v1/assets/{id}/replace` | the draft and `sourcesDigest` | 201 | `{successor: AssetDto, succession}` — the new asset and the archive's succession row |

An asset that is not there is **404 `no_such_asset`** on all three.

**The offer** is `{eligible, held, replacedBy, predecessor, schedules, groups, setupOffered,
seasonOffered, notesOffered, tags, parentChoiceIds, prefill, childNames, openLoan}`: `eligible` is true
iff the asset is not transferred out (`held`) and has no successor (`replacedBy`, a succession row or
`null`); `predecessor` is the asset; `schedules` its own unarchived schedules as the `/v1` schedule row (a
schedule has a time rule iff its `timeInterval` is not `null`); `groups` the groups it can carry; the three
`…Offered` flags say whether set-up (readings and quick actions), the season and the notes can be carried;
`tags` its **active** bindings as `NfcTagDto`; `parentChoiceIds` the parents the editor's rule allows;
`prefill` the form's starting `{name, category, location, parentAssetId}`; `childNames` and `openLoan` are
named, never moved. A transferred-out asset still answers 200, `held: true`.

**The draft** is strict — an unknown key is a **400**, `predecessorId` included, since the predecessor is
the path's:

| key | type | default |
|---|---|---|
| `retiredOn` | `YYYY-MM-DD` or `null` — required iff the old asset is not retired, ignored once it is | `null` |
| `successor` | the new asset: `name` (required), `category`, `manufacturer`, `model`, `serialNumber`, `purchaseOn`, `inServiceOn`, `purchasePriceMinor`, `currency`, `vendor`, `location`, `warrantyExpiresOn`, `warrantyNotes`, `parentAssetId` — the asset command's keys without `description`, `notes`, `templateKey`, `seasonStartMmdd` and `seasonEndMmdd`, each of which is a **400** | required |
| `carrySeason`, `carrySetup`, `carryNotes` | booleans | `false` |
| `manualPhase` | `IN_SEASON`｜`OUT_OF_SEASON` or `null` — required iff `carrySeason` on a `MANUAL` season | `null` |
| `scheduleIds`, `groupIds` | ids from the offer | `[]` |
| `scheduleStartOn` | `YYYY-MM-DD` or `null` — required iff a ticked schedule has a time rule; the phone's form default is not applied here | `null` |
| `movedTagIds` | binding ids from the offer's `tags`, **each named on its own** — there is no "all", label or pattern form | `[]` |
| `sourcesDigest` | the plan's, on `replace` only — missing there is a **400**; a string on `replace-plan` is a **400** (`null` is tolerated) | — |

The keys are pinned in `command-shapes.json` as `replaceDraft` and `replaceSuccessor`.

**The plan** is `{eligible, blockedBy, replacedOn, problems, sourcesDigest}`. `blockedBy` is `null`,
`asset_transferred_out` or `ASSET_ALREADY_REPLACED` — the refusal `replace` would answer first, which no
draft can fix. `replacedOn` is the succession's date: the old asset's `retiredOn` when it is retired, else
the draft's `retiredOn` trimmed, and `""` when there is neither. Each problem is
data, `{code, field, problem}`, with the code and field it would be refused with (**The #92 codes**,
below). `sourcesDigest` is the lowercase-hex SHA-256 over the draft as decoded — its id lists sorted and
without duplicates, `sourcesDigest` left out — then `replacedOn`, then every row the replacement reads, as
archive rows: the old asset, its succession row, each ticked schedule and group, each moved binding and,
with `carrySetup`, every reading definition and quick action. **A client never computes it**: it sends
back the plan's digest with the same draft. Key order, spacing and id-list order do not matter; every
value does, as sent — the API trims and drops nothing, so a value the replacement ignores (a
`manualPhase` without `carrySeason`, a `retiredOn` on a retired asset) still counts.

**The apply** refuses in one order, and writes nothing on any refusal: a malformed draft **400**; **404**;
**409 `asset_transferred_out`**; **409 `ASSET_ALREADY_REPLACED`**, `problems`
`ReplacedBy(successorAssetId=…)`; a digest other than the plan's — the draft changed, or the asset or a
row reviewed with it changed — **409 `REPLACE_STALE`**, `field` `sourcesDigest` (a malformed digest is a
mismatch, so a 409 too); the plan's problems **422**, the first's code and field, every one in
`problems`; then the one write, which checks everything again inside its own transaction and can still
answer **409 `REPLACE_STALE`** or **`asset_transferred_out`**; then **201**. On `REPLACE_STALE`, re-read the
offer and plan again; never resend the old digest.

**A replay** — the same apply after a success, or after a lost answer — is **409
`ASSET_ALREADY_REPLACED`** naming the successor, and a re-plan says `eligible: false`, `blockedBy:
ASSET_ALREADY_REPLACED`; there is never a second successor. Two applies that race each other give one
successor, and the loser answers `REPLACE_STALE`.

**Tags move by binding id only, and never through NFC (R92-2).** Each id in `movedTagIds` re-targets that
one binding row to the new asset in the same write — its id, payload, key, label and hardware id kept, only
its target and `updatedAt` new. No tag is written, read or touched: there is no NFC I/O on this path or
anywhere in this API, `/v1/tags` stays read-only, and every binding not named stays with the old asset.
The old asset keeps its id and its whole history; everything carried is a new row.

### Supply items (#15)

Five rows over three new path shapes, at version 1. A **supply item** is one canonical product, replacement
item, consumable, module or pack an asset takes — a filter cartridge, a battery, a belt, a chemical — with a
stable `id`, its identity fields and an ordered list of generic **specifications**. It is a catalog row and
nothing more: no quantity, no fitted position, date or serial, and no file. A complete pack and an item
inside it are two unrelated supply items.

| method | path | body | success | notes |
|---|---|---|---|---|
| `GET` | `/v1/supply-items` | — | 200 | `{supplyItems: [SupplyItemDto]}`, **archived included** (each carries its `archivedAt`), by name casefolded, then `id` |
| `POST` | `/v1/supply-items` | `{name, category?, manufacturer?, model?, partNumber?, preferredUnit?, notes?, specifications?}` | 201 | `{supplyItem}`; an absent text field is `""`, an absent `specifications` is none |
| `GET` | `/v1/supply-items/{id}` | — | 200 | `{supplyItem, assetSupplies: [AssetSupplyDto]}` — every applicability row naming it, by `assetId`, `role`, then `id` |
| `PATCH` | `/v1/supply-items/{id}` | the same keys, every one optional | 200 | `{supplyItem}`; an **overlay**, below. An edit that changes nothing is a 200 carrying the stored row, and `updatedAt` does not move |
| `POST` | `/v1/supply-items/{id}/archive` | `{"archived": true｜false}` | 200 | `{supplyItem}`; reversible. Archiving leaves the item's applicability rows and every line link alone |

`SupplyItemDto` is `{id, name, category, manufacturer, model, partNumber, preferredUnit, notes, archivedAt,
createdAt, updatedAt, specifications}`, and each specification is `{id, key, label, value, unit, sortOrder}`
— the archive's own rows (`data.json`'s `supplyItems`, specifications nested). `category` is free text, not
the asset catalog; `partNumber` is the one identity field for an SKU or a part number. A specification's
`value` is plain text: no range, no condition, no interval.

**A specification row** in a `POST` or `PATCH` body is `{id?, key?, label, value, unit?}`. `label` and
`value` are required and may not be blank. `key` is the row's stable machine name, in the reading key's
rule — a lower-case letter, then up to 39 lower-case letters, digits or underscores. Absent, `null` or `""`
asks for none, and a **new** row then takes its label's slug (`"Micron rating"` → `micron_rating`; `spec`
when the label slugs to nothing; `_2`, `_3`… appended when another row of the item holds it); a typed key
must fit the rule and may not repeat another row's. `id` names a row this item already holds: that row
**keeps its id and its stored key**, even when its label changes, unless a key is typed. Any other `id` —
none, another item's, a made-up one, a repeat — is a new row with a fresh id. Rows are stored in the order
sent, and `sortOrder` is the row's position. An absent `unit` is `""`, on a kept row too: a stored row sent
back without its `unit` stores no unit, so a client re-sending a row sends its `unit` with it.

**The `PATCH` is an overlay** (R15-16). Every key is optional, and **absent or `null` leaves the stored value
alone** — no supply item field is nullable, so the two mean the same thing. **A given `""` clears** an
optional text field — `category`, `manufacturer`, `model`, `partNumber`, `preferredUnit` or `notes`; text is
trimmed, so `"  "` clears too. **`name` is never blank**: `""` is 422 `SUPPLY_ITEM_NAME_REQUIRED`, never
"unchanged". **`specifications`, when given, is the whole ordered list**: a stored row left out is removed,
and `"specifications": []` removes every row. An absent `specifications` sends the stored rows back with their
`id` and `key`, so each keeps both. A `PATCH` saves the whole item, so an item that arrived by an import in a
form this build would not have written — untrimmed text, say — is rewritten in this build's form by its first
edit, however few keys that edit names.

**Nothing deletes a supply item.** It is archived, never removed (R15-5): `DELETE /v1/supply-items/{id}` is a
**405**, as is any other verb a shape does not take, and any other sub-path is a 404. An archived item stays
on the assets that take it and on every line that names it, and takes no **new** applicability row
(`SUPPLY_ITEM_ARCHIVED`). Every refusal is in **The #15 codes**, below.

### Asset supplies (#15)

Four rows over three new path shapes. An **applicability row** says that an asset — any asset, a child asset
included — takes a supply item in a **role** ("Prefilter", "Stage 2", "Spare"). An asset may take several
supply items, and one supply item in several roles. The row is configuration, not history: it has no
position, no date, no serial and no notes.

| method | path | body | success | notes |
|---|---|---|---|---|
| `GET` | `/v1/assets/{id}/supply-items` | — | 200 | `{assetSupplies: [AssetSupplyDto], supplyItems: [SupplyItemDto]}` — the asset's rows by `role`, then `id`, and **each supply item they name once**, by name casefolded, then `id`. The **twenty-sixth** `/v1/assets/{id}/…` sub-resource, so a verb it does not take is a **404**; a held asset reads as any other |
| `POST` | `/v1/asset-supplies` | `{assetId, supplyId, role}` | 201 | `{assetSupply}`; all three are required |
| `PATCH` | `/v1/asset-supplies/{id}` | `{role}` | 200 | `{assetSupply}`; `role` is the row's only editable field, so it is **required** — a body without it is the **400**. A re-role to the role the row already holds is a 200 carrying the stored row, and `updatedAt` does not move |
| `DELETE` | `/v1/asset-supplies/{id}` | — | 204 | the row goes; the asset and the supply item stay. The one delete verb #15 adds (R15-5) |

`AssetSupplyDto` is `{id, assetId, supplyId, role, createdAt, updatedAt}`, the archive's own row. **The role
is cleaned** as an asset category's display text is: invisible characters such as a zero-width space
dropped, the text trimmed, and every run of spaces — a no-break space included — made one space. A role blank
once cleaned is `ASSET_SUPPLY_ROLE_REQUIRED`. **Uniqueness is exact on the cleaned text**: the triple
`(assetId, supplyId, role)` is unique, so a second row in the same role is `ASSET_SUPPLY_TAKEN`, while "Oil
filter" and "oil filter" are two roles. Moving a row to another asset or another supply item is a `DELETE`
plus a `POST`. `/v1/asset-supplies` takes only `POST` and `/v1/asset-supplies/{id}` only `PATCH` and
`DELETE`, so a `GET` on either is a **405**: an asset's rows are read through its sub-resource, an item's
through `GET /v1/supply-items/{id}`.

`supplyId` names a supply item by its id, and **`""` is not "none"**: it names no supply item, so it is
refused as unknown, **404 `NO_SUCH_SUPPLY_ITEM`**. An `assetId` that is not on this phone is the shipped
**404 `no_such_asset`**. A `POST`, a re-role or a `DELETE` of a row of an asset transferred out from this
phone answers the shipped **409 `asset_transferred_out`**, after every check above; a re-role that changes
nothing writes nothing, so it is still the 200.

**Material lines carry the link.** A quick action's `consumables` line (**save-profile**) and an event's or a
completion's `consumables` line take an optional `supplyId` beside `name` and `unit`, which stay the line's
readable snapshot: editing, renaming or archiving the supply item never rewrites a line. Every profile and
event answer carries `supplyId` on each line, `null` when unlinked. Absent and `null` both mean unlinked, and
**those requests are full replaces**: an edit that leaves `supplyId` off a line clears that line's link, and
an event's lines are matched by their position. An archived supply item may be named. A `supplyId` naming no
supply item — `""` included — is the shipped **422 `profile_validation`** or **`event_validation`**, `field`
`consumables`, problem `UnknownSupplyItem(index=…)`; there is no new code for a line. **Nothing links a line
by its name**: a line named exactly as a supply item stays unlinked until a client sends its `supplyId`. A
completion's lines may carry `supplyId`; a completion sent without lines writes no line, so it names no
supply item.

In an archive (format 18) the two lists travel as `supplyItems` (specifications nested) and `assetSupplies`,
and each material line carries its `supplyId`; an import-merge reports the two tallies `supplyItems` and
`assetSupplies`. An incoming applicability row that a local row under another id already holds rides on
`ASSET_SUPPLY_HELD_BY_AN_EQUIVALENT_LOCAL_ROW` (an `IDENTICAL`) when the two agree field for field, and on
`ASSET_SUPPLY_HELD_BY_A_LOCAL_ROW` (a `SKIPPED`) when only their stamps differ; the local row stays as it was.

### Installed components (#47)

Six rows over five new path shapes, at version 1. An **installed component** is a physical, serviceable
part, assembly or position fitted inside an asset or inside another installed component — a battery tray,
the pack in it, a membrane in its housing — stored as **one row per fitted instance**: its asset, an
optional parent row of the same asset, a name, an optional **direct** supply item (`supplyId`: this unit
is one of these), an optional ordered **composition** of supply items (this unit is made of these), an
optional serial or lot, an optional install date, a removal date once it leaves, the row it replaced, a
sibling order and notes. An asset's **current** rows are the ones with no `removedOn`; a removed row is
its history, and keeps its own composition. Each write is the one row it names — and, on a remove or a
replace, the rows that write closes — and a link or an entry is there only because a client sent it.

| method | path | body | success | notes |
|---|---|---|---|---|
| `GET` | `/v1/assets/{id}/installed-components` | — | 200 | `{installedComponents: [InstalledComponentDto], supplyItems: [SupplyItemDto]}` — every row of the asset, **current and removed**, by `id`, each with its `composition`, and **each supply item a row or an entry names once**, a removed row's included, by name casefolded, then `id`. The **twenty-seventh** `/v1/assets/{id}/…` sub-resource, so a verb it does not take is a **404**; a held asset reads as any other |
| `POST` | `/v1/installed-components` | `{assetId, parentId?, name, supplyId?, composition?, serialOrLot?, installedOn?, notes?, sortOrder?}` | 201 | `{installedComponent}`; **install**, below |
| `GET` | `/v1/installed-components/{id}` | — | 200 | `{installedComponent}` |
| `PATCH` | `/v1/installed-components/{id}` | `{name?, supplyId?, composition?, serialOrLot?, installedOn?, notes?, sortOrder?}` | 200 | `{installedComponent}`; an **overlay**, below. An edit that changes nothing is a 200 carrying the stored row, and nothing is written |
| `POST` | `/v1/installed-components/{id}/remove` | `{removedOn}` | 200 | `{installedComponent, closed: [InstalledComponentDto]}` — the removed row, and every current row inside it that the same write closed, by `id` |
| `POST` | `/v1/installed-components/{id}/replace` | `{replacedOn, name?, supplyId?, composition?, serialOrLot?, notes?}` | 201 | `{installedComponent, replaced, closed: [InstalledComponentDto]}` — the new row, the row it replaced (now removed), and every current row inside that one that the same write closed, by `id` |

`InstalledComponentDto` is `{id, assetId, parentId, name, supplyId, composition, serialOrLot, installedOn,
removedOn, replacesId, sortOrder, notes, createdAt, updatedAt}`, and each entry of its `composition` is
`{id, supplyId, quantity, unit, sortOrder}` — the archive's own rows (`data.json`'s `installedComponents`,
the composition nested), every key written, `null` included. `parentId` is `null` for a row fitted
straight into its asset, `supplyId` for a row that names no supply item, `installedOn` when no install date
is recorded, `removedOn` while the row is current, and `replacesId` unless the row replaced another. Dates
are `YYYY-MM-DD` days, `quantity` is a JSON number, and a row's entries come in `sortOrder`, then `id`, order.

**The composition** says what one unit is made of — a pack made of four of one battery is one row whose
composition is one entry, that battery's `supplyId` with `quantity` `4`:
a quantity is how many of that SupplyItem one unit is made of; nothing is counted, kept or used up.
An entry in a body is `{id?, supplyId, quantity, unit?}`. `supplyId` names a supply item. `quantity` is a
JSON number above zero; a quoted number, `true` or `null` is the shipped **400**. An absent `unit` is
`""`, and a `null` one is the **400**. The entries are stored in the order sent, and an entry's `sortOrder`
is its position in that list, set by the phone: a body that sends `sortOrder` inside an entry is the
**400**, so a client re-sending a row's composition sends each entry as `{id, supplyId, quantity, unit}`.

**Install** (`POST /v1/installed-components`). `assetId` and `name` are required, and `name` is trimmed. An
absent `parentId` fits the row straight into its asset; a sent one names a current row of the same asset,
and is read as sent, as an asset's `parentAssetId` is — `""` names no row, so it is **404
`NO_SUCH_INSTALLED_COMPONENT`**, `field` `parentId`. An absent, `null` or `""` `supplyId` names no supply
item, and an absent, `null` or `""` `installedOn` records no install date. An absent `composition` is none,
and an absent `serialOrLot` or `notes` is `""`; for those three a `null` is the **400** — absent means
empty, as on a supply item's create. An absent `sortOrder` puts the row after its current siblings (one
more than the greatest, `0` for the first); a sent one is a whole number from 0 to 1,000,000, and any
other is the **400**. A date is no later than the phone's today. The answer is the new row, current, with
`replacesId` `null` and its entries under fresh ids.

**The `PATCH` is an overlay.** Every key is optional, and **absent or `null` leaves the stored value
alone**. **A given `""` clears** `supplyId` (the row then names no supply item), `installedOn` (no install
date recorded), `serialOrLot` and `notes`. **`name` is never blank**: `""` is 422
`INSTALLED_COMPONENT_NAME_REQUIRED`, never "unchanged". **`composition`, when given, is the whole ordered
list**: `"composition": []` empties it, and an absent `composition` keeps the stored entries with their
ids. An entry sent with the `id` of an entry this row holds keeps that id **at its first occurrence**; a
repeated id, or one the row does not hold, is a new entry with a fresh id. `sortOrder` places the row among
its siblings, on the bound above. A `PATCH` edits a current row and a removed one alike — a correction. Its
keys are the seven above: `assetId`, `parentId`, `removedOn` and `replacesId` are unknown keys, the shipped
**400**, so a row stays on its asset and under its parent, and closes only by a remove or a replace. An
archived supply item is accepted as the direct `supplyId` only when the row's stored link is that item, and
in an entry only when the stored composition already names it; anywhere else it is `SUPPLY_ITEM_ARCHIVED`.

**Remove** (`POST …/remove`). `removedOn` is required. The row closes on that date, and **so does every
current row inside it, at any depth**: the subtree closes together, on the same date and in the same
write. Each closed row keeps its composition, and nothing is deleted. `removedOn` is on or after the
row's install date and that of every current row inside it (`INSTALLED_COMPONENT_REMOVED_BEFORE_INSTALLED`),
and a removed row is closed already (`INSTALLED_COMPONENT_REMOVED`).

**Replace** (`POST …/replace`). One write closes the row and installs its successor in its place — the
same asset, parent and `sortOrder` — with `installedOn` = `replacedOn` and `replacesId` naming the closed
row; every current row inside the closed one closes on the same date, so the successor starts with no rows
inside it. `replacedOn` is required. **Only an absent or `null` `name` is filled from the replaced row** — a
label. **An omitted, `null` or `""` `supplyId` is none, and an omitted, `null` or `[]` `composition` is
none**: the successor carries exactly the link and the entries the body sends, so a client that keeps the
replaced row's sends them, and every entry of the successor gets a fresh id, whatever `id` it is sent with.
An absent `serialOrLot` or `notes` is `""`. A replace that omits `name` reads the replaced row for it first,
so one aimed at a row that is not there is the **404 `NO_SUCH_INSTALLED_COMPONENT`** before the body is
judged.

**The order of the checks.** A body the decoder refuses is the **400** first. Then the body's own
problems — a blank `name`, a malformed or future date, a quantity not above zero — every one in
`problems`, the first answering. Then the rows the request names, in order, the first that fails
answering alone: on an install the asset (`no_such_asset`), the parent (`NO_SUCH_INSTALLED_COMPONENT`
`field` `parentId`, `INSTALLED_COMPONENT_PARENT_ON_ANOTHER_ASSET`, `INSTALLED_COMPONENT_PARENT_REMOVED`),
then the direct `supplyId` (`NO_SUCH_SUPPLY_ITEM` or `SUPPLY_ITEM_ARCHIVED`, `field` `supplyId`, answered
alone, with no entry's problem beside it), then every entry's supply item, collected (`field`
`composition`); on a remove or a replace the row (`NO_SUCH_INSTALLED_COMPONENT`, then
`INSTALLED_COMPONENT_REMOVED`) before anything else it names. A write to a row of an asset transferred out
from this phone answers the shipped **409 `asset_transferred_out`** after every check; an edit that changes
nothing writes nothing, so it is still the 200. Every refusal is in **The #47 codes**, below.

**Nothing deletes an installed component.** A remove closes it and keeps it as history:
`DELETE /v1/installed-components/{id}` is a **405**, as is any other verb a shape does not take —
`GET /v1/installed-components`, `GET …/remove`, `DELETE …/replace` — and any other sub-path is a 404.

**Child assets are another thing.** `POST /v1/assets/{id}/components`, the `components` key of
`GET /v1/assets` and the health answer's `components` are **child assets**: assets in their own right, each
with its own tags, schedules and history. An installed component is a row inside an asset, read and
written only through the routes above.

In an archive (format 19) the rows travel as `installedComponents`, each with its `composition` nested;
`/v1/status` counts `installedComponents`, every row, current and removed, and `compositionEntries`, every
entry of every row; and an import-merge reports the tally `installedComponents` (**Table 23**).

## What has no endpoint, deliberately

A wipe. A replace-restore. An export. Writing an NFC tag. Binding an NFC tag. Provisioning a tag.
Deleting an asset, a reading or a quick action. Deleting an attachment (since #92 the API lists, reads,
amends and adds them, **Attachments (#92)**), and, other than an upload adding a new file,
reading or writing an attachment's bytes. Anything at all for the pre-split `externalLinks`
tombstones. **Recording an attachment's source provenance** other than by saving a reference as a
document (**Save as document (#92)**; an upload never records one) has no endpoint either; an import-merge
carries an archive's sourced rows as they are. And, since 1.2: **deleting a schedule, a group or a membership row**; **deleting or
amending a closure** — it is immutable exported history, and a client that could edit one could
rewrite a schedule's past; a **snooze**, which is device-local delivery state and not canonical
data; a **second completion path** — `POST /v1/events` has no `scheduleId`, `occurrenceOn`,
`detailsPending` or `source` field, so each of them is an unknown field there and a completion can
only be written through `POST /v1/schedules/{id}/complete`. And, since 1.3: **deleting a
reference** — the API adds and amends, the phone removes, exactly as it does for an attachment and a
closure. And, since 1.4: **amending or deleting a condition or an activation** — both are immutable
facts, appended and never rewritten; **deleting a health subject** — archiving is the only way one
leaves; and **writing a health value** — health is computed at read time and stored nowhere. And,
since #79: **the warranty warning itself** — posting, dismissing or re-announcing it — which is
device-local delivery state like the snooze; **writing a warranty status**, which is derived;
**deleting a service case** — a `CANCELLED` or `CLOSED` status entry is the exit; **amending or deleting a
timeline entry**, which is immutable; and **writing a case's status or `closedOn`** other than through a
status entry. And, since #72: **deleting a loan** (`DELETE /v1/loans/{id}`) — "Mark returned" is the
only exit, and a returned loan is history; **reopening or editing a returned loan**; **relinking a loan**
to a contact, or making a link at all — only the phone picks from Contacts; **any contact read** — no
route reads, searches or returns a contact or its lookup URI; and **the loan reminder itself** — posting,
dismissing or re-announcing it — which is device-local delivery state like the snooze. And, since #77:
**a Transfer Pack** — making, sharing, saving or importing one — **marking** an asset transferred out,
**withdrawing** a transfer record, and **listing** the transfer records; each is the phone's alone, and
`/v1/status` only counts the records. And, since #86: **amending or removing a succession**, or recording
one other than by a replacement — a new one is recorded only by the phone's Replace asset or, since #92,
`POST /v1/assets/{id}/replace`, a merge only inserts an archive's rows (**Table 20**), and
`/v1/assets/{id}/succession` only reads. And, since #92: **a download job or a poll** — Save as document
answers when it is done; **listing every attachment** (`GET /v1/attachments`); and **anything under
`/v1/attachments/{id}/`**. And, since #15: **deleting a supply item** (`DELETE /v1/supply-items/{id}`) —

(where one is fitted, and since when, is an installed component's, since #47). And, since #47:
**deleting an installed component** (`DELETE /v1/installed-components/{id}`) — a remove closes it and
keeps it as history. Each of these is
absent because **nothing routes to it** — a request for one is a 404,
or a 405 where the path shape exists for another verb (`DELETE /v1/assets/{id}`,

## Errors

Every failure answers with the envelope below, except three: a 401, a framing refusal (the 400,
405 and 413 rows of **Framing and limits** — those carry no body at all), and
`/v1/import-merge/apply`'s 409, which carries the merge report.

Since #92 a request can also end with **no answer at all**: the connection closes and nothing more is
sent. That happens when an upload's own stream fails (a read timeout, a reset, its 10-minute deadline) and
when the screen leaves during an upload or a save as document. Nothing is written — except a write into
the folder that had already begun, which completes. Treat it as an unknown outcome and read before you
send the request again (**Attachments (#92)**, **Save as document (#92)**).

```json
{"error": {"code": "…", "message": "…", "problems": ["…"], "field": null}}
```

`field` (1.4) names the one body key a refusal is about, and is `null` where a refusal is not about
exactly one key. The 1.4 codes marked in their table below fill it — `policyOffsetDays`, `name`,
`occurredOn`, … — and so do the four 1.1.0 validation families (**The 1.1.0 validation families**,
below), the 1.4 malformed-value rows (after **The 1.4 codes** table), #79's warranty reminder and
service case families, and #72's loan family. The rule is the same for all
of them: a problem about one key names that key; a problem about a pair names the pair's first key
(`seasonStartMmdd` for the season window); and a problem that names a reading's id but not the
request key that sent it answers `null`, because the id is already in `problems`. Every other answer
carries `null`. #92's codes fill it on the same terms (**The #92 codes**, below): a key of the upload's
`X-ServiceTag-Attachment` object is named as a body key is (`operationKey`, `sha256`, `displayName`,
`capturedOn`), and a key inside the replace draft's `successor` gives `field` its first dotted form,
`successor.<key>` — `successor.name`, `successor.purchaseOn`, `successor.currency`, ….

| 422 | `REFERENCE_URI_INVALID` | the URI does not parse, carries no scheme, or is a hierarchical scheme with an empty host — so `https://` alone, `https:///path`, `file:///etc/passwd` and a bare `notaurl` are all refused, while an opaque scheme with no authority such as `joplin:x-callback-url/openNote?id=…` is fine. Also an over-long URI, over 2,048 characters |
| 422 | `REFERENCE_SCHEME_BLOCKED` | a hard-blocked scheme — `javascript`, `file`, `content`, `intent`, `android-app`, `tel`, `sms`, `mailto` — **and an unfamiliar one**, which over this API is a refusal and never a confirmation |
| 422 | `REFERENCE_ROLE_NOT_ALLOWED` | since #91: a `role` on a reference that is not a web link — a `POST` whose URI is not `http` or `https`, or a `PATCH` giving a role to a `NOTE_LINK` or `OTHER` row. The one code in this table with a `field`: `field` `role`. On a `POST` an invalid or blocked URI answers its own code first, and this one comes before a blank name, an unknown asset and a taken URI; on a `PATCH` an unknown id and a blank name come first. Nothing is written. A `null` role is never refused |
| 409 | `REFERENCE_URI_TAKEN` | that asset already holds this URI. The same URI on a **different** asset is ordinary and permitted |

Two things this table deliberately does not have. There is no code for **deleting** a reference,
because `/v1/references/{id}` takes no `DELETE` and nothing routes to one. And a `POST` naming an
`assetId` that is not on this phone answers the shipped **404 `no_such_asset`** — 1.1.0's
`lower_snake` code, reused verbatim — rather than a new `UPPER_SNAKE` twin, because it is the same
fact this API already names and one condition should not have two codes.

One more code exists in the source and is **not** in the table above, on the same footing as
`SCHEDULE_INVALID` and `GROUP_INVALID`: **`REFERENCE_UNCHANGED`**. The mapper carries an arm for it
so that every refusal the domain can raise has a code and a new one is a compile error, but **no
route can return it** — a `PATCH` whose values already match the stored row is answered 200 with
that row, before anything becomes an error at all. It is a value `error.code` cannot carry, which is
why the six above are the whole list a client branches on.

A refusal here carries an empty `problems` list on purpose: the sentence in `message` names the
field or the rule, and never a URI, a scheme, an authority or a path. `field` is `null` on every
refusal here except `REFERENCE_ROLE_NOT_ALLOWED`'s, which is `role`.

`FETCH_NOT_HTTPS` and `FETCH_HAS_CREDENTIALS` are defence only: the mapper spells them, and no request
receives them — a first hop that breaks either rule is `REFERENCE_NOT_MATERIALIZABLE`, and a redirect that
breaks either is `FETCH_REDIRECT_REFUSED`. The address rule needs the host resolved, so a host that resolves
to a local address is `FETCH_LOCAL_ADDRESS`, on the first hop or any later one; only `localhost` (and
`*.localhost`) is refused before the fetch. A permission denial is `NETWORK_DENIED` whichever
layer found it. The upload's header problems — the header absent, padded, not base64url, not UTF-8, not
JSON, an unknown key or name — are the shipped **400 `bad_request`**, whose message says which. A
`REPLACE_STALE` on a malformed digest is deliberate: there is no digest-format code, and the remedy — plan
again — is the same.

## The additive merge import

Semantics from issue #44. The endpoints read an ordinary ServiceTag **data** archive — the
`ServiceTag-data-*.zip` half of a backup set, **format 1–19** — through the same `BackupCodec` a
restore uses. A format-6 archive carries the maintenance groups, the schedules and the occurrence
closures; an older one simply has none of them, and restoring it never invents a schedule. A
format-8 archive also carries season activations, condition rows and health subjects; a format ≤7
one decodes its schedules' season fields through the legacy mapping (**Deprecated inputs**) and has
none of the three. A format-10 archive also carries each attachment's document role (#67), and a
format-11 archive each asset's warranty reminder lead (#79); an older archive whose assets carry a
non-null lead is corrupt, and refused before any plan exists. A format-12 archive also carries the
service cases and their timeline entries (#79); an older archive carrying either is corrupt, refused the
same way. A format-13 archive also carries the loans (#72), open and returned, each with its contact link
as data; an older archive carrying one is corrupt, refused the same way. A format-14 archive also carries
the transfer records (#77), `OUT`, `IN` and `WITHDRAWN`, and never the graph of an asset its own records
hold: an archive that holds one, or an older archive carrying a record, is corrupt, refused the same way.
A format-15 archive also carries the asset successions (#86), both assets of each in the file, no asset
replaced twice or replacing twice, and no loop: an archive that breaks one of those, or an older archive
carrying a succession, is corrupt, refused the same way.
A format-16 archive also carries each attachment's source provenance (#85); an older one whose attachments
carry any is corrupt, refused the same way.
A format-17 archive also carries each reference's document role (#91), `"role": null` when it has none; an
older one whose references carry any is corrupt, refused the same way, and so is a format-17 archive
naming an unknown role or giving one to a reference that is not a web link.
A format-18 archive also carries the supply items (#15), each with its specifications, the asset supplies,
and each material line's `supplyId`, `null` when unlinked; an older one carrying a supply item, an asset
supply or a non-null line `supplyId` is corrupt, refused the same way (an explicit `null` is accepted), and so
is a format-18 archive whose line or applicability row names a supply item or asset not in the file, whose
specification lacks a label or a value, repeats a key or carries one outside the key rule, whose role is not
stored cleaned, or that holds one `(assetId, supplyId, role)` twice.
A format-19 archive also carries the installed components (#47), each with its composition; an older one
carrying an installed component is corrupt, refused the same way, and so is a format-19 archive that
repeats a row's or an entry's id, whose row names an asset, a parent, a supply item — directly or in an
entry — or a replaced row that is not in the file, whose parent is on another asset or whose current row
sits under a removed parent, whose replaced row is on another asset, under another parent, current, itself
or replaced twice, whose parents or replacements come back round, or whose row has a blank name, a
malformed date, a removal before its install, or a quantity not above zero.
`plan` decides; `apply` decides again and writes.

**It is planned before it writes, and "incoming wins" is not a thing it can do.** Per row:

| verdict | when |
|---|---|
| `INSERT` | the id is not on this phone, every reference it makes resolves, and no unique index objects |
| `IDENTICAL` | the id is here and **every** backup-format field matches, `createdAt` and `updatedAt` included (an asset's `category` compared by its normalised key since #74, for an archive of any format; an attachment's document role compared only for an archive of format 10 or later since #67 — an older archive cannot carry one, so its attachments are compared without the role and — when the row here carries one — without the last-modified stamp that giving it moved; every other field still counts, so a role given on this phone since that export is still `IDENTICAL`, while in a format-10 archive a different role, a role against none here, or none against one here is a `CONFLICT`; and, since #79, an asset's `warrantyReminderLeadDays` compared only for an archive of format 11 or later, on the same rule — an older archive cannot carry one, so its assets are compared without the lead and — when the asset here carries one — without the `updatedAt` that setting it moved, so a lead set on this phone since that export is still `IDENTICAL`, while in a format-11 archive a different lead, a lead against none here, or none against one here is a `CONFLICT`; and, since #91, a reference's document role compared only for an archive of format 17 or later, on the same rule — an older archive cannot carry one, so its references are compared without the role and — when the reference here carries one — without the `updatedAt` that giving it moved, so a role given on this phone since that export is still `IDENTICAL`, while in a format-17 archive a different role, a role against none here, or none against one here is a `CONFLICT`, or `SKIPPED` when the row here is the same asset and URI under another id; and, since #15, a material line's `supplyId` compared only for an archive of format 18 or later, on the same rule — an older archive cannot carry one, so a quick action or an event whose lines here carry a link is compared without its lines' `supplyId` and without the `updatedAt` that giving them moved, so a pre-#15 export re-plans `IDENTICAL` on a line linked on this phone since; every other field still counts, and a link given and then removed leaves the moved `updatedAt` and no link, which is a `CONFLICT`; in a format-18 archive a different link, a link against none here, or none against one here is a `CONFLICT`) — or a local NFC tag under a different row id already is this tag, field for field — or, for a category, the key is here with the same display — or, since format 18, a local applicability row under a different row id already is this row, field for field (`ASSET_SUPPLY_HELD_BY_AN_EQUIVALENT_LOCAL_ROW`) |
| `SKIPPED` | the plan declined it. In 1.1.0 the two reasons are `ATTACHMENT_STORE_NOT_CONFIGURED` (no attachment folder is picked on this phone) and `ATTACHMENT_BYTES_ABSENT`; format 8 adds `HEALTH_SUBJECT_SCHEDULE_HELD_BY_A_LOCAL_ROW`, format 9 `CATEGORY_KEY_HELD` and `CATEGORY_IS_BUILT_IN`, and format 18 `ASSET_SUPPLY_HELD_BY_A_LOCAL_ROW`. The report carries only `conflicts`, so a skipped row shows as a count and not as a reason |
| `CONFLICT` | anything else. See the codes below |

**A merge only ever inserts.** There is no update verdict: an id that is already here either matches
or conflicts, so **no row this phone already had can be modified or deleted by a merge**. And
**there is no partial merge**: one conflict anywhere means `apply` writes nothing at all and answers
409 with the conflict list.

**Identity is a UUID, or an NFC payload identity — never a name**, with one designed exception: a
category (format 9) *is* its normalised name (see **Table 15** below). A tag is matched on
`(payloadFormat, payloadKey)` as well as on its row id, so the same physical tag cannot end up bound
to two assets. The NFC hardware UID is informational and is never identity. Matching
manufacturer, model and serial number — when all three are non-blank on both the incoming and the
local asset — produces a `duplicateCandidates` entry — a **review hint**, never an action. Matching
names do not even hint.

**Timestamps never pick a winner.** `updatedAt` is compared like any other field and read for
nothing else.

**Write order is dependency-safe**: categories first (format 9; nothing references them), then
assets in topological order (parents first), then maintenance
groups (whose members reference assets), then ENTERED readings, then DERIVED ones, then quick
actions, then schedules (which reference an asset or a group, a reading and a quick action), then
occurrence closures (which reference a schedule), then tombstone links, tag bindings, events, and
attachment rows, references, and — since format 8 — season activations and conditions (which
reference an asset, and softly an event) and health subjects (an asset, and softly a schedule), and
— since format 12 — service cases (an asset, and softly two events) and then their timeline entries (a
case), and — since format 13 — loans (an asset), and — since format 15 — the successions (their two
assets), and — since format 14 — the transfer records last of all,
after every row they describe (a record names its asset by id alone, and has no owner). A row whose parent or owner is neither on this phone nor being inserted by the
same plan is a conflict (`OWNER_NOT_AVAILABLE`), not an orphan.

**An attachment row is written only when the folder holds the bytes the row claims.** Four answers,
in this order: another local row already claims the locator → `ATTACHMENT_LOCATOR_TAKEN`, a
conflict; there is no attachment folder at all → **skipped**, `ATTACHMENT_STORE_NOT_CONFIGURED`
(and `applicable` stays true — the other six tables still merge); nothing is at the locator →
**skipped**, `ATTACHMENT_BYTES_ABSENT`; bytes are there but their size or sha256 is not the row's →
`ATTACHMENT_BYTES_DIFFER`, a conflict, because a diverged file is a diverged overlap and not a
missing one. So a merge can never leave a row pointing at a file that is not there, and never leave
one whose recorded hash does not describe what is stored. No byte is ever written by a merge;
restoring bytes is still the Backup screen's job.

One honest gap: the size-and-hash check runs just before the transaction, not inside it, because
there is no transaction that spans the database and a document provider. A file deleted or replaced
in that window still yields an inserted row whose hash no longer describes the bytes on disk. The
next `RestoreArtifacts` reports it.

`ASSET_SUPPLY_HELD_BY_A_LOCAL_ROW` on a `SKIPPED`. The second of those is how two phones
that closed the same round on the same day merge cleanly: a closure has no mutable field, so a
re-imported unchanged one is always `IDENTICAL`. `HEALTH_SUBJECT_SCHEDULE_HELD_BY_A_LOCAL_ROW` is how an incoming health subject that

written: its `detail` names the local subject. The two category codes are Table 15's (below).

**Tables 12–14** (format 8). A season activation and a condition are immutable facts matched on
their id alone: `IDENTICAL` when every field matches, `CONTENT_DIFFERS` otherwise, `INSERT` when the
id is new — never an update, and never a change to their asset's row. Their `eventId` is a soft link
and never an owner. A health subject is matched on its id, then on the schedule it drives, then on
its asset and schedule as owners; an archived subject claims no schedule.

**Table 15** (format 9, #74). A category's identity is its normalised key, so the same category
typed on two phones is one row. An incoming row is `INSERT` when the key is new here, `IDENTICAL`
when this phone holds the key with the same display (timestamps are never compared), and `SKIPPED`
— never a conflict — when a built-in owns the key (`CATEGORY_IS_BUILT_IN`) or this phone holds it
under another spelling (`CATEGORY_KEY_HELD`; the local spelling wins). The plan also **plans the
promotion**: a category an inserted asset needs that no built-in, local row or accepted row holds is
an `INSERT` decision of its own, spelled as the oldest such asset spells it, and every inserted asset
is written in its canonical spelling with its own `updatedAt`. An asset's `category` is compared by
key, so a pre-upgrade export's `appliance` against this phone's `Appliance` is `IDENTICAL`, and
re-planning an applied archive is all `IDENTICAL`, or `SKIPPED` for a category row a built-in or a
differently spelled local row holds — those stay `SKIPPED` on every re-plan. So the proof that an
archive has been applied is **`applicable` with zero `INSERT`**, not "every verdict `IDENTICAL`": two
phones whose categories were spelled differently show `CATEGORY_KEY_HELD` for ever. Two costs are accepted: an archive made before a
rename to a new key brings the old key back as an unused row, and a deleted category comes back
from an archive that holds it.

**Tables 16–17** (format 12, #79). A service case is matched on its id alone, with its asset as its
owner: `IDENTICAL` when every field matches, `CONTENT_DIFFERS` otherwise, `OWNER_NOT_AVAILABLE` when its
asset is neither here nor being inserted, `INSERT` when the id is new — never an update. Its
`incidentEventId` and `resolutionEventId` are soft links and never owners. A timeline entry is an
immutable fact owned by its case, on the conditions' terms: `IDENTICAL`, `CONTENT_DIFFERS` or `INSERT`,
and `OWNER_NOT_AVAILABLE` when its case is neither here nor accepted by the same plan. An entry is a row
of its own, so a note added on one phone re-merges as an entry `INSERT` beside an `IDENTICAL` case; a
status entry moves the header too, so a case whose status moved on one phone after the other received
it is `CONTENT_DIFFERS` on re-merge.

**Table 18** (format 13, #72). A loan is matched on its id alone, with its asset as its owner, and
compared on every field, its contact link included: `IDENTICAL` when every field matches,
`CONTENT_DIFFERS` otherwise, `OWNER_NOT_AVAILABLE` when its asset is neither here nor being inserted,
`ASSET_ALREADY_LENT` when it is open and its asset holds a different open loan here, `INSERT` otherwise —
**never an update**. So a return, a re-date, a mode change, a relink or a note made on one phone after the
other received the loan is `CONTENT_DIFFERS` on re-merge, and a returned loan inserts beside a local open
one. Only this phone's open loans are asked about: the archive itself holds one open loan per asset, or it
is corrupt.

**Table 19** (format 14, #77). A transfer record is an immutable fact matched on its id alone:
`IDENTICAL` when every field matches, `CONTENT_DIFFERS` when some field differs. A record that is not here
is judged against this phone's records together with every record the archive brings: an `IN` or a
`WITHDRAWN` that would close an `OUT` open here is `ASSET_TRANSFERRED_OUT` — an ordinary archive never
brings an asset back, and a withdrawal is repeated on each phone, never merged; an `OUT` that would leave
its asset with two open `OUT`s is `TRANSFER_DIVERGED`; anything else is an `INSERT` — so another
installation's `OUT` holds the asset here too, even while its row here reads `ACTIVE`. Then — for an
archive of any format, since this phone's own records can hold an asset — with the records the plan would
insert, no row may land for or against an asset held here: a row the plan would insert that a held asset
owns — by the write guard's one ownership rule: the asset itself or a component under it; its
definitions, profiles, attachments (its own and its events'), events, references, season activations, conditions, health
subjects, service cases and their entries, loans, links and tags; a schedule on it, and that schedule's
closures; and a group with any row, current or removed, naming it, with the group's schedules — is
`ASSET_TRANSFERRED_OUT`, and so is a row whose insert would leave a staying row naming a held asset's rows,
so a plan never calls applicable an apply the write refusal would stop. The records are written last, and
the `transfers` tally counts them. **A merge never replaces**: only the phone's pack import returns an
asset, and it is the one write that replaces rows (**Transferred-out assets (#77)**, above).

**Table 20** (format 15, #86). A succession is an immutable fact matched on its id alone, every field
compared: `IDENTICAL` when every field matches, `CONTENT_DIFFERS` when some field differs — **never an
update** (MS1). One that is not here is judged in this order: `OWNER_NOT_AVAILABLE`, `detail` naming the
asset, when its predecessor or its successor is neither here nor being inserted by the same plan (MS2);
`SUCCESSION_TAKEN` when another succession — this phone's, or one the plan still inserts — already names its
predecessor as a predecessor, or its successor as a successor (MS3); `SUCCESSION_CYCLE` when, with this phone's successions and the plan's
that still stand, it would sit on a loop (MS4); then `ASSET_TRANSFERRED_OUT` when either of its assets is
held here (**Table 19**'s rule, M2); `INSERT` otherwise. The successions are written after both of their
assets and the loans, before the transfer records, and the `successions` tally counts them.

**Tables 21–22** (format 18, #15). A supply item is matched on its id alone, every field compared, its
specifications in their order included: `IDENTICAL` when every field matches, `CONTENT_DIFFERS` when some field
differs — a rename, a specification edit or an archive on one phone — **never an update**, so the whole archive
is refused (R15-7). One that is not here is `CHILD_ROW_ID_TAKEN` when a specification's id is held by another
supply item, here or earlier in the same plan, and `INSERT` otherwise. The supply items are decided **before the
quick actions and events**, so a line naming a supply item the same plan inserts resolves; a line naming one that
is neither here nor being inserted is `OWNER_NOT_AVAILABLE`, `detail` naming it, on its quick action or event. An
applicability row is matched on its id, every field compared; one that is not here is `OWNER_NOT_AVAILABLE` when
its asset, then when its supply item, is neither here nor being inserted; then, when a local row under another id
holds the same `(assetId, supplyId, role)`, `IDENTICAL` with `ASSET_SUPPLY_HELD_BY_AN_EQUIVALENT_LOCAL_ROW` if the
two agree field for field, `SKIPPED` with `ASSET_SUPPLY_HELD_BY_A_LOCAL_ROW` if they differ (in practice their
stamps) — nothing is written either way, and the local row stays; `INSERT` otherwise, unless its asset is held
here, which is `ASSET_TRANSFERRED_OUT` (**Table 19**'s rule, M2). The supply items are written after the assets,
the applicability rows after both their owners, and the `supplyItems` and `assetSupplies` tallies count them.

**Table 23** (format 19, #47). An installed component is matched on its id alone, every field compared, its
composition in its order included: `IDENTICAL` when every field matches, `CONTENT_DIFFERS` when some field
differs — a row removed, replaced, edited or recomposed on one phone since the export — **never an update**,
so the whole archive is refused. One that is not here is judged in this order: `CHILD_ROW_ID_TAKEN` when an
entry's id is held by another installed component, here or earlier in the same plan; `OWNER_NOT_AVAILABLE`,
`detail` naming it, when its asset, then the first supply item it names — its direct `supplyId`, then its
entries' — then its parent is neither here nor being inserted by the same plan (a parent the plan refuses
included); `INSTALLED_COMPONENT_REPLACEMENT_TAKEN` when another installed component — this phone's, or one the
plan inserts earlier — already names the row it replaces; `INSERT` otherwise, unless its asset is held here,
which is `ASSET_TRANSFERRED_OUT` (**Table 19**'s rule, M2). The rows are decided and written parents first,
after the assets, the supply items and the applicability rows, and the `installedComponents` tally counts
them. An older archive carries none, and the rows here are left out of its plan.

**The dev ↔ production limit.** A merge never retires anything and never updates a row, and that limit
stands. A replacement that retired its old asset did so on the phone that made it, so merging that phone's
export into another that holds the old asset unretired meets `CONTENT_DIFFERS` on the old asset's row, and
nothing lands — neither the new asset nor the succession. And two phones that each replaced the same asset
cannot both keep their succession: merging one into the other meets `SUCCESSION_TAKEN`. Make the
replacement on the phone that should keep it, or take a Replace restore there from a backup of the phone
that made it — which, like every Replace restore, loses whatever the restored phone had that the backup lacks.

**Between plan and apply.** `apply` does not execute a plan it was handed: it re-reads this phone
inside its own transaction and re-decides, so a plan is never applied to a state it was not just
checked against. If the answer has changed, it refuses with 409 rather than writing a different
thing than the plan said.

A corrupt archive, or one from a newer build, is refused **before** any plan exists: the phone is
byte-identical afterwards.

**What the plan checks, exactly.** Every uniqueness constraint the database actually declares: on a
tag's payload identity, a reading's key per asset, a quick action's `(action, reading)` pair, an
event's `(source, sourceRef)`, an attachment's storage locator, a membership window's
`(group_id, asset_id, added_at)`, a completion's `(schedule_id, occurrence_on, asset_id)` and a
closure's `(schedule_id, occurrence_on)` — plus every aggregate child-row primary key, the
at-most-one-open-window rule, a closure's **second identity**, which is matched independently of
its row id, and — since format 8 — the rule that a schedule drives at most one live health subject.
Plus every foreign key, and the asset tree's no-cycles rule.

**Known limits in 1.1.0.** Resolving a conflict, and mapping an imported asset onto a local one
(#44's interactive slice), are a later release — 1.1.0 merges what is unambiguous and refuses the
rest. The bytes half of a backup set (`ServiceTag-artifacts-*.zip`) has no endpoint. A merged quick
action may end up sharing its name with a local one on the same asset: the app keeps those names
unique when *you* create one, but the schema has no unique index on them, so the merge does not
invent a rule the database does not have. And a `(source, sourceRef)` collision is always a
conflict, never a coalesce candidate — #44 allows the softer reading, and it needs the interactive
slice to be useful.
