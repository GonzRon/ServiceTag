## Lane A — B01 close-round window guard (`B01-close-round-window.md`)
Contract: in `CloseRound.run`, after the existing target/archived/already-closed/complete/actionable checks and BEFORE any write, derive the current state (`recompute.stateOf(schedule)`); with `due = state.effectiveDueOn` and `lead = schedule.leadDays` (0 when null), if `today < due − lead` throw a new `ScheduleCommands` problem `OccurrenceNotYetOpen(id, occurrenceOn, opensOn = due − lead)`; no row is written. Today is the device-local date already used by the use case; `effectiveDueOn` is the engine's local date, so no UTC skew can enter. The `closedOn` range check that follows is unchanged. API: `ApiJson` maps it to **409 `OCCURRENCE_NOT_YET_OPEN`** ("this round has not reached its due-soon window, so there is nothing to abandon yet"); `docs/api/v1.md`: add the code row beside `OCCURRENCE_NOT_CLOSEABLE`, and REPLACE the close-round paragraph's sentence "The next round opens the moment a round is closed … before retrying rather than sending the call again." with the 1.2.1 rule (closable from `due − lead` through today; a repeated close after the schedule advanced is refused with the new code and writes nothing). Spec §2.9: a dated 1.2.1 amendment note under the existing range rule. UI: `ScheduleDetailViewModel.canClose` gains the fifth question, computed from the same three values the state already holds (`effectiveDueOn`, the schedule's `leadDays`, `today`) — never a status word — so the action and the use case cannot disagree; `CloseRoundDialog`'s date range is unchanged. MCP: one docstring sentence on `close_round` naming the refusal. Tests (hazards): core — refused the day before the window with no row; allowed on the boundary day; allowed when overdue; **the retry**: close, then close again the same day → refused with the new problem and one closure remains; route — 409 `OCCURRENCE_NOT_YET_OPEN`; view model — `canClose` false the day before the window and true on it; the API-doc code table test (if one exists) updated.
