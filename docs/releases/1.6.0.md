# ServiceTag 1.6.0

ServiceTag 1.6.0 (version code 19) is a feature release. It adds a searchable asset list when you share something into ServiceTag and a role on a web link, and it lets your paired workstation do the jobs that used to need the phone in hand: an asset's documents, Save as document and Replace asset. It installs in place over 1.5.0.

## Choosing the asset when you share (#93)

Sharing a link, a document, a photo or a note into ServiceTag now starts with the same list as the Assets tab: the same search box, the same **Type**, **Components** and **Archived** controls, and the same rows in the same order. Type a few letters of the asset's name, type, make, model, serial number or location to narrow the list, then tap the asset. As on the Assets tab, archived assets and components stay out of the list until you turn on **Archived** or **Components**, and an asset you have transferred out is never offered.

The next screen names the asset you chose, with **Change** to go back and pick another; Back does the same, and keeps the name and description you typed. Nothing else about sharing has changed: the name, description, type and role, and the way the link, document or note is saved, work exactly as before.

## A role on a web link (#91)

A web link on an asset can now say what it is for, with the same roles a document has: **Purchase invoice or receipt**, **User manual** or **Service manual**. Choose one when you add an http or https link with **Add link** or share one into ServiceTag, and change or clear it later with **Edit** on the link's ⋮ menu. Only you set it: ServiceTag never guesses a role from a link's name, address or title. A note link, or a link with an unfamiliar scheme, takes none.

The role shows as a quiet line under the link's kind in **References**. A link is still not a key document: the asset's key documents and its purchase document list only saved documents. **Save as document** now starts its review with the link's role already chosen, and you can change or clear it before you save.

Links you saved before this release have no role until you give them one. Roles travel in backups, merges and Transfer Packs, and the Developer API and the MCP tools can set, change and clear them.

**One change a script could meet:** on two Developer API routes, editing a reference (`PATCH /v1/references/{id}`) and Save as document (`POST /v1/references/{id}/materialize`), a request body that is not strict JSON is now refused as a bad request. Two fields with no comma between them used to be accepted. Over the API, Save as document with no `role` now takes the link's own role; send `"role": null` (in the MCP tools, `clear_fields=["role"]`) to save it with none.

## Your workstation can do the phone-only jobs (#92)

**Your workstation can now do the jobs that used to need the phone in hand.** While the Developer API screen is open and paired, the workstation's tools can:

- read an asset's documents;
- add a document from the computer, up to 256 MB, and say what it is (a manual, a receipt) at the same time;
- change a document's name, type, date, notes or role;
- save one of an asset's web links as a document;
- replace an asset: first a plan that changes nothing, then the replacement itself.

A replacement moves only the NFC tags you name, one by one, and it never writes to a tag: the tag simply opens the new asset from then on. Adding the same file again for the same job is recognised and not duplicated.

The phone now tells a paired workstation a random ID for this installation of ServiceTag. The ID is not tied to the hardware and never goes into a backup, an export or a Transfer Pack.

**One thing to know:** a paired workstation can add a web link to an asset and then ask the phone to save it. So a paired workstation can have the phone download a file from any public https address. Every Save as document rule still applies: https only; never into your own home network; at most 256 MB and ten minutes; only real document types; no login cookies.

The phone still listens only to itself, only while that screen is open, and only to a workstation that has the pairing code shown there. Nothing on the phone's screens changed for this, and it adds nothing to the data format or to backups.

## Upgrading

- 1.6.0 installs in place over 1.5.0, and your data stays.
- The database moves to schema 17 and backups to format 17, in one step at first launch. Older backups still import — restore and merge — as before.
- An older ServiceTag, 1.5.0 or earlier, refuses a backup or a Transfer Pack made by this release as too new, rather than dropping what it cannot read.
- Web links you saved before this release have no role until you give them one.
- One change a script could meet: on `PATCH /v1/references/{id}`, a request body that is not strict JSON — two fields with no comma between them — is now refused with 400 Bad Request; it used to be accepted. The new `POST /v1/references/{id}/materialize` refuses it the same way.

## Known limits

- After **Change** on the share screen, the list starts again from the top; your search and filters are kept.
- On a byte share with no document folder set, the form's button reads **Close**, and Back on that form returns to the asset list rather than closing — both leave nothing saved.
- Over the Developer API, adding a document holds the phone's long-write lock for up to its ten-minute deadline; another upload or Save as document waits.
- Over the MCP, `replace_asset` guards only its own plan-then-apply: a change made after a separate `plan_only` review is applied unseen unless you plan again right before confirming.

The Developer API's contracts — every route, field and refusal named here — are in [`docs/api/v1.md`](../api/v1.md).
